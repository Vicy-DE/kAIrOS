# kAIrOS Docker testrig — dev + hardware test, everything inside Docker

Test/development environment for **kAIrOS**: boot the appliance image in a QEMU/KVM VM,
optionally with a real NVIDIA GPU handed to the VM (VFIO), and verify it the way the project
verifies every release — by the image's own boot-log verdict. The host only provides Docker,
`/dev/kvm` and (for GPU runs) the vfio-bound GPU — every tool (QEMU/OVMF, python/aiohttp,
build toolchain, ssh/test harness) lives in the `kairos-testrig` image.

This is the in-repository copy of the owner's rig (`pod/` next to the repo on the reference
laptop). It is path-independent: every host path comes from `.env` (copy `.env.example`) and
defaults to `dev/rig/work/` (gitignored). The long-form guide is
[docs/how-to/VM-TEST-RIG.md](../../docs/how-to/VM-TEST-RIG.md).

```
┌─ host: Ubuntu 26.04 (reference laptop) ──────────────────────────┐
│  amdgpu → laptop display          vfio-pci → RTX 4070 (10de:2820)│
│  ┌─ docker: kairos-testrig ──────────────────────────────────┐   │
│  │  dev: repo + models + tests (mock engines)               │   │
│  │  vm:  QEMU/KVM + OVMF ──► kairos-hwtest-4070.img         │   │
│  │        └─ vfio-pci passthrough: the REAL 4070 in the VM  │   │
│  │           SSH :2222 · kAIrOS UI :1337 · VNC :5900        │   │
│  └───────────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────┘
```

## One-time host setup

```bash
cd dev/rig
cp .env.example .env            # edit: KAIROS_HOME (where the .img lives), models, knowledge, engines
sudo bash host-setup.sh         # docker + vfio bind config + rig SSH key + .env VFIO_GROUP (idempotent)
# → REBOOT once if you let it write the vfio-at-boot config (the running desktop holds the
#   NVIDIA DRM node; after the reboot vfio-pci owns the card from the start). On a hybrid
#   laptop whose display runs on another GPU you can instead keep the host driver and rebind
#   live per run: KAIROS_SKIP_VFIO=1 sudo bash host-setup.sh, then gpu-to-vfio.sh / gpu-to-host.sh.
sudo bash host-setup.sh status  # expect: READY FOR GPU VM: YES
```

Without a GPU: `host-setup.sh` is optional — Docker, `/dev/kvm` and `docker compose build`
are all the `dev` service needs.

## Use

```bash
cd dev/rig
docker compose build                                  # the rig image (ubuntu:24.04 + qemu/ovmf/python)

# development / CI (no GPU):
docker compose run --rm dev bash                      # shell: repo at /workspace/repo
docker compose run --rm dev /workspace/repo/dev/rig/testrig/vm.sh test   # boot the image, no GPU

# hardware test (GPU vfio-bound):
docker compose run --rm vm                            # boot + SSH checks + nvidia-smi on the real GPU
docker compose run --rm vm /workspace/repo/dev/rig/testrig/vm.sh smoke   # + real image generation
docker compose run --rm --service-ports vm /workspace/repo/dev/rig/testrig/vm.sh run   # interactive: VNC :5900, UI :1337
docker compose run --rm vm /workspace/repo/dev/rig/testrig/vm.sh fresh   # reset guest to factory-fresh first boot

# the GPU desktop in one command (host side; rebinds the GPU live, provisions x11vnc in the guest):
bash testrig/run-gpu-vm.sh
```

Always pass the mounted `vm.sh` path explicitly: the copy baked into the image (`/rig/vm.sh`)
goes stale when the tree changes. For the mock-engine test suite use
[`dev/docker/run-suite.sh`](../docker/run-suite.sh) instead (trixie + quickjs — this
ubuntu-based image lacks the JS gate's parser and two tests skip).

The pristine `kairos-hwtest-4070.img` (`KAIROS_IMG`) is never modified — the VM writes to a
qcow2 overlay (`KAIROS_OVERLAY`, default `/images/testrig-overlay.qcow2`, virtual `VM_DISK`
= 60G so the first-boot auto-resize is exercised; an image larger than that gets an overlay of
its own size). Guest login: `root` with
`testrig/id_kairos` (generated by `host-setup.sh`, `make-key.sh`, or `vm.sh` itself on first
use; images built before R66 still take the password `kairos` — every script tries the key
first and falls back). **An image only trusts the key whose `.pub` was in
`iso/secrets/authorized_keys` when it was built** — so a downloaded image cannot be reached
over SSH at all, and `vm.sh test` then stops at "no SSH" (sshd answers `Permission denied
(publickey)`). Build your own image with your key, point `KAIROS_SSH_KEY` at the key the image
was built with, or judge it without SSH: boot it, then read `KAIROS-LOGS/latest.json` from the
overlay's EFI partition — the unprivileged commands are in
[VM-TEST-RIG.md, "Judging an image you cannot log in to"](../../docs/how-to/VM-TEST-RIG.md#judging-an-image-you-cannot-log-in-to).
The console log (`/images/testrig-console.log`) holds only the firmware's lines (the image boots
quiet); QEMU's VNC (port 5901) is not published — reach it at the container's address.

## Pass criterion: the boot-log verdict

`vm.sh test` runs 16 checks (19 with the GPU, 20 with `smoke`). The one that matters is **bootlog verdict**:
the image's own `kairos-bootlog` writes `KAIROS-LOGS/latest.txt` + `latest.json` to the EFI
partition after every boot, with `verdict` PASS / WARN / FAIL. PASS and WARN pass; FAIL fails.
An empty `systemctl --failed` is deliberately *not* the criterion — it was satisfied twice by an
unusable machine (black screen, kernel crash-looping; `docs/VM-TEST-2026-09-10.md`). The json
of the run is copied next to the console log as `/images/testrig-latest.json`.

## Sync the working tree into a booted guest

`testrig/sync-guest.sh` pushes the repo into the guest at `/opt/vibeos/os` **and** replicates
what the image build applies (the `iso/config/includes.chroot` overlay, unit enables, loader
entries, fonts, the boot screen), so a synced guest boots the same chain a freshly built image
does. It ships a built engine set from `KAIROS_ENGINES` (`KAIROS_SYNC_ENGINES=0` keeps the
image's). After a sync, **reboot the guest** so the whole chain runs on the new code.

```bash
# no GPU: the dev service (host ports 2223/1338); with the GPU: the vm service (2222/1337/5900)
docker compose run -d --service-ports --name kairos-sync dev /workspace/repo/dev/rig/testrig/vm.sh run
docker exec kairos-sync /workspace/repo/dev/rig/testrig/sync-guest.sh      # once SSH is up (~1-2 min)
docker exec kairos-sync bash -c 'ssh -p 2222 -i /workspace/repo/dev/rig/testrig/id_kairos -o StrictHostKeyChecking=no root@127.0.0.1 reboot'
```

## Network trust boundary of the guest [R66]

The kAIrOS kernel (root, :1337) binds **127.0.0.1 only** by default — the kiosk is on the
machine. The host-side `:1337` forward therefore works only after the guest opted in:
`vm.sh test|smoke`, `run-gpu-vm.sh` and `sync-guest.sh` all pipe `testrig/expose-ui.sh` over
SSH, which writes `/etc/systemd/system/kairos.service.d/expose-ui.conf` (`VIBEOS_HOST=0.0.0.0`)
and restarts the kernel once per overlay. Even exposed, everything that changes the machine
(install / format / power / settings / model downloads / fs writes) refuses a non-loopback
caller without the guest's per-boot token:

```bash
TOKEN=$(docker exec kairos-user-vm bash -c 'ssh -p 2222 -i /workspace/repo/dev/rig/testrig/id_kairos -o StrictHostKeyChecking=no root@127.0.0.1 cat /run/kairos/token')
curl -X POST http://localhost:1337/api/settings -H "X-Kairos-Token: $TOKEN" -H 'Content-Type: application/json' -d '{"key":"accent","value":"#ff0000"}'
# or open the UI as an operator:  http://localhost:1337/?token=$TOKEN
```

Read-only monitoring (`/api/status`, `/api/hw`, `/api/models`, `/api/install/status`,
generation jobs) needs no token.

## The GPU lock

One GPU, many jobs: every process that touches the GPU on the host — a VM with passthrough, the
desk-window kernel, a benchmark — runs under `flock $KAIROS_HOME/.gpu.lock` (`KAIROS_GPU_LOCK`),
so two jobs never fight over 8 GB of VRAM and a run's timings are never contaminated.
`desk-window.sh start` and the project's benchmark units do this; wrap your own GPU commands
the same way: `flock "$KAIROS_HOME/.gpu.lock" <command>`.

## Files

| file | purpose |
|---|---|
| `.env.example` | host paths (`KAIROS_HOME`, `KAIROS_MODELS`, `KAIROS_KNOWLEDGE`, `KAIROS_BIN`, `KAIROS_ENGINES`), `VFIO_GROUP`, GPU PCI ids |
| `env.sh` | sourced by the host scripts: loads `.env`, fills the defaults |
| `host-setup.sh` | idempotent host prep: docker, vfio-pci bind, groups, rig key, `.env` |
| `make-key.sh` | the rig's SSH key pair + staging of the `.pub` into `iso/secrets/authorized_keys` (no sudo) |
| `docker-compose.yml` | `dev` (no GPU) + `vm` (VFIO GPU) services |
| `gpu-to-vfio.sh` / `gpu-to-host.sh` | hand the GPU to vfio-pci for a VM / back to the host driver, live (sudo) |
| `desk-window.sh` | the kAIrOS desktop in a Firefox window on this machine: kernel in a container (`start` = on the GPU with real weights, `ui` = no GPU, `server` = `ui` headless: no window, prints the URL; `--no-window` for `start`/`ui`) |
| `stick-logs.sh` | after a real stick run: copy `KAIROS-LOGS`, journal, X logs off the stick (read-only) and write `SUMMARY.txt` |
| `stick-patch.sh` | the pattern for patching a flashed stick in place (needs a patch bundle that is not in the repo) |
| `testrig/Dockerfile` | the all-in-one dev+test image (ubuntu:24.04; the guest is Debian trixie) |
| `testrig/vm.sh` | boot/verify the image in QEMU (`test` / `run` / `smoke` / `fresh`) |
| `testrig/sync-guest.sh` | working tree + build-hook equivalents + engine set into a booted guest |
| `testrig/expose-ui.sh` | in-guest opt-in: kernel listens on 0.0.0.0 so the host reaches :1337 [R66] |
| `testrig/gpu-display-setup.sh` | in-guest: X on the NVIDIA GPU + x11vnc on :5900 |
| `testrig/run-gpu-vm.sh` | host: GPU rebind + VM + expose + GPU display, one command |
| `testrig/dist-clean.sh` | in-guest, before flattening an overlay into a release image |
| `testrig/feature-test.sh`, `testrig/feature-test-gpu.py` | in-guest end-to-end feature drivers on the real GPU (app, image, video, music, game, vision) |
| `testrig/historical/` | how earlier images (v5, the Krea 2 bundle, the July fixes) were provisioned; need artefacts that are not in the repo |

## Why VFIO instead of the container toolkit

The goal is testing the **bootable hardware image** against real GPU silicon — driver DKMS
build, post-boot `nvidia-load.service`, hybrid-GPU behavior, engines on sm_89. Only a VM with
the physical GPU passed through exercises that whole stack; a compute container would test the
host's driver, not the image's.

# Fixes 2026-10-24 — the HDMI helper waits for X, the flaky dock test, TearFree for the two-CRTC desktop

Three small fixes the owner approved after the v7.5-4 card run of 2026-10-24 (the first run with R90's one desktop over
the panel + the USB-C monitor and R91's `kairos-hdmi-prime`; verdict PASS, 28 min). They go into the next card image.

## 1. `kairos-hdmi-prime` loaded the NVIDIA display modules before X (R91 design vs reality)

**Cause (the card's logs).** `docs/HDMI-PRIME-2026-10-22.md` says the helper loads `nvidia_modeset` + `nvidia_drm`
*after X is up*. On the card it did not: `kairos-hdmi-prime.service` is `Type=simple` with `Before=getty@tty1`, so its
main `boot` path runs *alongside* the boot and waited for the nvidia module only — bound at 06:02:53, modules loaded at
**06:02:56**; `getty@tty1` started at 06:02:57, the X attempt at **06:03:06** (uptime 24.9 s), `xinitrc: started` at
uptime 48.4 s. X then applied Debian's `nvidia` OutputClass to `/dev/dri/card1` and loaded `nvidia_drv.so`; with
`AutoAddGPU off` no G0 screen was made and the X start time did not change — no stall this time, but not the design.

**Change (`iso/config/includes.chroot/usr/local/sbin/kairos-hdmi-prime`, `boot` path).** Before the module wait the
helper waits until X is *really* up — `x_up`: an X attempt of this boot exists (`/run/kairos/x-attempts` ≥ 1), the `:0`
socket exists, **and** the running attempt's `xinitrc: started` breadcrumb is in this boot's `x.log` (the attempt's
header precedes its session, its exit line ends it; `.bash_profile` rotates `x.log` at attempt 1). The socket alone is
not enough: the server listens before it probes the GPUs (dix: `CreateWellKnownSockets` precedes `InitOutput`); the
breadcrumb is printed by the client xinit starts only once the server signalled it is ready, i.e. after the GPU probe
and the screen init. The wait is bounded (`KAIROS_HDMI_XUP`, 180 s) and logged either way: `X up after Ns (socket +
'xinitrc: started' of X attempt N)` or `X not up after Ns (socket: …, X attempts: …) — probing anyway` (after the bound
the probe goes ahead — the status quo of the card run, harmless with `AutoAddGPU off`). The attach-at-boot and the
consent paths (`react`, `attach-now`, `later`, `on`) are unchanged; the unit file only gained the comment.

**Proof.** `tests/test_hdmi_prime.py`: `hp_boot_loads_modules_after_x` (a mocked timeline — the attempt + its socket at
0.3 s, the breadcrumb at 1.6 s: the fake modprobe's write is stamped after the breadcrumb, the wait is logged; the
previous boot's x.log and an exited session do not count; after the bound the probe goes ahead; `react` never waits) and
the contracts test (the order X wait → module wait → probe in the `boot` case, `x_up`'s three conditions, the new
override). VM boot (no NVIDIA): see §4.

## 2. The flaky dock test

`dock_e2e_records_states` (`tests/test_dock_browser.py`) failed once in R91's suite run 2: it asserted the dock icon's
`naturalWidth == 48` the instant the dock had rendered, before the `<img>` had loaded. Test-only change: a bounded wait
(≤ 3 s) for `img.complete && naturalWidth === 48`, then the test continues as before. Proof: the test run 10× in a row
in the suite container (§4).

## 3. Page flips of the one desktop window on the 780M (tearing / stutter risk)

**Finding.** The card's `Xorg.0.log` has **77 ×** `(WW) AMDGPU(0): flip queue failed: Invalid argument` (each with
`Page flip failed` + `(EE) present flip failed`) in 28 min; the v7.5-2 run with the per-screen kiosks had 0 in 13 h. The
first ones come 18 s after `xinitrc: started`, once per second for ~25 s (the clock tick repaints), then sporadically.
The kernel's `amdgpu … Mode Validation Warning: Viewport size failed validation` lines were there before (39 vs 48).

**Reading.** The lines come from the DDX's `amdgpu_do_pageflip` → `drmModePageFlipTarget` (EINVAL) under a Present flip
(`amdgpu_present_flip`): Chromium presents the screen-sized kiosk window (4480×1440 over the eDP CRTC at 0,0 and the
DP CRTC at 1920,0) by DRI3 page flips, and the DDX flips the *client's* buffer onto both CRTCs. When the kernel refuses
one, the frame is **copied** into the front buffer unsynchronised — a torn / stuttering frame. Why the kernel refuses
(the client buffer's modifier / pitch / format against a CRTC's scanout rules, or the ~4480-px surface split over two
pipes) cannot be read from the log; the fix below removes the shared flip altogether.

**Change: `TearFree on` for amdgpu** (`iso/config/includes.chroot/etc/X11/xorg.conf.d/22-kairos-tearfree-amdgpu.conf`,
installed by `build-img.sh`, shipped by the rig sync's etc overlay). What the image supports (read from the v7.5-4 image
with debugfs, read-only): `xserver-xorg-video-amdgpu 23.0.0-1`, `xserver-xorg-core 2:21.1.16-1.3+deb13u2`, Mesa 25.0.7.
`amdgpu(4)` there: *"Option TearFree: Set the default value of the per-output 'TearFree' property, which controls tearing
prevention using the hardware page flipping mechanism. TearFree is on for any CRTC associated with one or more outputs
with TearFree on. Two separate scanout buffers need to be allocated for each CRTC with TearFree on. … If this option
isn't set, the default value of the property is auto, which means that TearFree is on for rotated outputs, outputs with
RandR transforms applied and for RandR 1.4 secondary outputs, otherwise off."* The card's log confirms the default:
`(==) AMDGPU(0): TearFree property default: auto` — off for the panel and the USB-C monitor.

- **Expected effect.** Each CRTC gets two scanout buffers of its own size; a client frame is copied into the CRTC's back
  buffer and that buffer is flipped at the CRTC's vblank. No shared 4480-px client buffer is flipped onto a CRTC any
  more (a DDX-allocated buffer cannot fail on the client buffer's properties), each monitor updates tear-free at its own
  refresh. The `flip queue failed` lines should go to 0.
- **Cost.** One extra GPU copy per frame and CRTC (≈ 26 MB per full 4480×1440 frame, a blit on the 780M), two more
  scanout buffers per CRTC (≈ 16 MiB for 1920×1080, ≈ 28 MiB for 2560×1440, in the iGPU's carve-out / GTT), up to one
  frame of added latency. The hardware cursor plane (R79) is unaffected.
- **How the option reaches the driver.** An `OutputClass` with `MatchDriver "amdgpu"` (the *kernel* driver) is merged into
  the autoconfigured device's options (`xf86MergeOutputClassOptions`; the mechanism `20-kairos-swcursor.conf` documents,
  and Debian's own `/usr/share/X11/xorg.conf.d/10-amdgpu.conf` uses for `HotplugDriver` — the card's log shows
  `Applying OutputClass "AMDgpu" options to /dev/dri/card0`). Only amdgpu is matched: the modesetting driver of the VMs /
  Intel and an NVIDIA boot GPU are untouched. Off without a rebuild: rename the file to `*.conf.disabled`, new X session.
- **The boot log measures it** (`kairos-bootlog`, new check `pageflip`, always PASS — a record, never a verdict change):
  `amdgpu TearFree <auto|on> (config present|absent); refused page flips (flip queue failed) in this X session's log: N,
  log up to uptime Ns`, plus an evidence block (the config, the Xorg log's TearFree / OutputClass lines, the counts of all
  three messages, the first and last refused flip, the kernel's viewport warnings this boot). On the card's log this
  reads `auto … 77`; the next run should read `on … 0`.
- **Proof so far.** The suite: `od_tearfree_amdgpu_conf_and_bootlog` (`tests/test_one_desktop.py`: the file's one
  section, amdgpu only, TearFree on and nothing else, the build + sync lists, the other X files unchanged; the real
  `kairos-bootlog` on a fake ESP with the card run's lines → `auto` / 77 + the first and last line in the evidence, a
  TearFree-on log → `on` / 0, a VM log → n/a). The two cursor tests (`desktop_pointer_swcursor_nocursor`,
  `imaging_cursor_hw_on_amdgpu_conf`) still hold: no active amdgpu SWcursor. A VM boots virtio, not amdgpu, so the option
  cannot be proven there — the VM boot (§4) proves it breaks nothing on non-amdgpu hardware. **The real proof is the next
  card run**: `pageflip` in `KAIROS-LOGS/latest.txt` must say `TearFree on` and a flip count of 0 (or near 0) over a
  session as long as this one, and the owner's eye: no tearing on either monitor while windows move across.

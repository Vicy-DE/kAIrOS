## 1. No mouse pointer — a design bug, invisible in every VM test

`startx -- -nocursor` plus `.xinitrc` setting the root window's cursor to an invisible 1×1 bitmap "for good"
(meant for the bare root during the boot-animation handover). Chromium sets no cursor of its own for the plain
arrow — its windows inherit the root's — so the whole desktop had no pointer. The VM tests drove input with
xdotool and never looked at the sprite.
**Fix:** after the kiosk launch `.xinitrc` sets `xsetroot -cursor_name left_ptr` (breadcrumb `xinitrc: pointer:`);
`unclutter -idle 2` hides it when idle. **Proven** on X in the build VM with XFixes `GetCursorImage`: moving over
the kiosk → 24×24 arrow, 272 opaque pixels; 8 s without movement → 1×1, 0 opaque (classic unclutter's effective
idle is a few seconds above its nominal 2 s).

## 2. Long boot — ~3½ min from power-on to the kiosk, all reads from the USB stick

Boot `#2` (no first-boot work), `systemd-analyze`: firmware 19.5 s + loader 4.4 s + kernel 5.9 s + userspace 2 min 36 s.

| item | time | cause |
|---|---|---|
| kairos-bootlog-early | 13.3 s on the critical chain (basic.target @21.7 s) | its closing global `sync` waited for every dirty page on the slow stick |
| nvidia-load | 48.7 s, getty@tty1 waited for it (graphical @70.5 s) | reading the 120 MB NVIDIA module + GSP firmware off the stick — on a hybrid laptop the panel does not need it |
| X start | ~72 s (startx @94.7 s, `xinitrc: started` @166.9 s) | Xorg, Mesa/LLVM (~200 MB) faulted in page by page from the stick |
| nvidia-persistenced | 86 s (off the critical chain) | GPU init after the slow module load |

**Fixes:** both boot-log scripts `sync -f` the EFI partition only; `kairos-gpu-setup` loads NVIDIA in the
background unless the NVIDIA card drives the monitor (the kernel picks CUDA per call from `/proc/driver/nvidia`,
the unit is RemainAfterExit); **`kairos-prewarm.service`** (only when the root is on USB, via its sysfs path):
phase 1 reads the desktop (Xorg, Mesa/LLVM, Chromium, openbox) sequentially at once, phase 2 the CUDA runtime,
llama-server, the baked LLM and the expander encoder at idle I/O priority if RAM holds them; timings in
`/var/log/kairos/prewarm.log`. **Not measurable in the VM** (NVMe-backed, no NVIDIA): the next stick run shows
the effect (`systemd-analyze` in the boot capture, prewarm.log).

## 3. No LLM — Gemma 4 took 7 min 23 s to load, the kernel waited 300 s

`/var/log/kairos/llama-server.log` (written since the 2026-10-06 logging work) + the kernel log of boot `#1`:

| UTC | event |
|---|---|
| 21:47:20 | first LLM request (a virtual-web page) → `starting llama-server (llm, cuda): Gemma 4 …` |
| 21:52:21 | `llama-server did not become healthy in 300 s` → the page failed |
| 21:52:34, 21:53:31 | two more pages: `503 Loading model` (the kernel found the process alive and sent at once) |
| 21:54:29 | app `starship-in-a-old-barn`: `503 Loading model` |
| 21:54:43 | Gemma `model loaded` after 443 s (13.6 GB → ~30 MB/s) |
| 21:55:05 | stopped again for an image request (swap strategy); boot `#2` never asked the LLM |

The stick reads **152 MB/s sequentially** (61 MB/s random 64 KiB) on this laptop's USB 3 port; llama.cpp's
mmap loading with the MoE experts on the CPU (`--fit`, "tensor overrides to CPU are used with mmap enabled")
reached a fifth of that.
**Fixes:** `LLAMA_LOAD_TIMEOUT` (env `VIBEOS_LLAMA_LOAD_TIMEOUT`, default 900 s); `llama_ready` + `wait_llama_health()`
— a request that finds llama-server alive but still loading waits for `/health` instead of meeting "503 Loading
model"; the load time is logged (`llama-server ready (llm, N s)`); kairos-prewarm phase 2 puts the model in the
page cache ahead of the first request (~90 s of sequential reading).

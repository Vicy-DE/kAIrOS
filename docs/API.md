# kAIrOS API — for apps running on this OS

Every kAIrOS app gets `window.vibe` injected. All calls return Promises.
This document is itself stored on the OS at `/system/docs/API.md` and served at `/api/docs`.

## Imagination & knowledge

| call | returns | notes |
|---|---|---|
| `vibe.ask(prompt)` | string | the OS language model; text/JSON on demand |
| `vibe.search(query)` | `{online, source, sources, results:[{title,snippet,url,source,lang}]}` | **offline-capable web search**: live web when online, the built-in encyclopedia otherwise — same shape either way. Offline, every installed ZIM answers (Wikipedia + the Wiktionary add-ons) and each hit's `source` says which ("Wikipedia (en)", "Wiktionary (de)") |
| `vibe.dict(word, from?, to?)` | `{word, from, to, entries:[{headword, display, pos, translations, source, from, to, match}], count, sources}` | **dictionary lookup** [R71 P3]: BEOLINGUS + FreeDict over en/de/es/fr/it/ja/ru (the `dictionaries` add-on); `to` defaults to the OS `language`, `from` may be omitted (every dictionary into `to` answers); exact → folded → prefix matches, `limit` ≤ 50; works with translation off; rejects while the add-on is missing |
| `vibe.browse(address)` | `{html, cached, grounded_by}` | the **imaginary web**: every page is generated by the AI (grounded in search facts), never fetched. Simplest use: `<iframe src="/web/any address">` — the same site as a real URL; links inside navigate the iframe by themselves (no `message` listeners, no postMessage plumbing — that mechanism is gone). Pages are cached → instant revisits, works fully offline |
| `vibe.image(prompt)` | URL of generated PNG | seconds — show a loading state |
| `vibe.images(prompts)` / `vibe.images(prompt, count)` | array of PNG URLs (in prompt order; `null` = that picture failed) | **several pictures in one run**: the model is loaded once for the whole list (a gallery of 4 ≈ 1 load + 4 renders instead of 4 loads). Options object instead of `count`: `{count, width, height, model, adult, expand}`. ≤ 12 per call; minutes for a long list — show progress |
| `vibe.video(prompt)` | URL of generated MP4 | minutes — explicit user action only |
| `vibe.vision(image, prompt)` | string | the OS **looks at a picture** [R70]: `image` = a `data:image/…;base64` URL (e.g. `canvas.toDataURL()`), a `/files/…` or `/genimg/…` URL, or `"screen"` / `"screen:N"` (the kiosk display / monitor N); seconds (model swap + one look); an add-on — try/catch |
| `vibe.game(prompt)` | `{slug, running, attempt, version, gate, window, pid}` | forge + launch a pygame game window — `running:true` = its window opened on the desktop (`gate:"mapped"`) |
| `vibe.forge(prompt)` | `true` | start a full **development cycle** in a new window: the OS writes the app AND generates the resources it needs (images, a music track, a video clip) — what the App Launcher uses |

## Filesystem — Android-style partitions

```
/system     write-protected. OS identity, manifest, prompts, these docs.
/data       read-write. Yours. Survives reboots. Reset by format().
```

| call | effect |
|---|---|
| `vibe.fs.list(path)` | entries `[{name, type, size, modified}]`; `vibe.fs.list("/")` shows partitions |
| `vibe.fs.read(path)` | file content as text (≤ 2 MB) |
| `vibe.fs.write(path, content)` | create/overwrite file under `/data` (parents auto-created) |
| `vibe.fs.mkdir(path)` | create directory under `/data` |
| `vibe.fs.delete(path)` | remove file or directory under `/data` |
| `vibe.fs.format()` | **wipe the whole `/data` partition** (factory reset). The OS itself asks the user to confirm in a dialog outside the app (an app cannot answer it); declined → the promise rejects with `cancelled: …`. Call it only from a clearly labelled button. No undo. |

Writes to `/system` fail with `read-only file system`. Path traversal (`..`) is blocked.
Convention: keep app files in `/data/<your-app-name>/…`.

## Hardware — the laptop-setup API

One namespace for everything a machine needs to be set up from inside the OS.
Missing hardware or tools never error: you get `{available:false, reason}` — render it.

| call | returns / effect |
|---|---|
| `vibe.hw.get()` | everything at once: `{wifi, battery, brightness, volume, display, bluetooth, airplane, datetime, memory_mb:{total,available}, disk_gb:{total,free}}` — nested objects: render fields (`hw.battery.percent`), never the object (prints `[object Object]`); `airplane` is a boolean; the settings recipe lists every field |
| `vibe.hw.wifi.status()` | `{available, enabled, connected, ssid, signal, bars, ip, connectivity, devices}` — `ssid` is the network's real SSID |
| `vibe.hw.wifi.scan()` / `.scan({fresh:true})` | `{networks:[{ssid, signal, bars, band, security, needs, saved, in_use}], age_s}` — the cached list at once, sorted by signal; `fresh` = a new radio scan (seconds) |
| `vibe.hw.wifi.connect(ssid, password?)` | `{ok, error, detail, connectivity}` — connects (and saves) a network; no password for `needs:"none"` (open, OWE) |
| `vibe.hw.wifi.disconnect()` / `.forget(ssid)` | `{ok}` — leave the network (profile kept) / delete every saved profile of that SSID |
| `vibe.hw.wifi.saved()` / `.on()` / `.off()` / `.signin()` | saved networks · radio on/off (kept across reboots) · open a hotspot's login page [R78] |
| `vibe.hw.bluetooth.*` / `vibe.hw.airplane.*` | devices, scan, pair (+ trust + connect), on/off · both radios at once — see "Bluetooth & airplane mode" below |
| `vibe.hw.battery()` | `{percent, status, charging, ac_plugged, health_percent}` |
| `vibe.hw.brightness.get()` / `.set(percent)` | screen backlight 1-100 |
| `vibe.hw.volume.get()` / `.set(percent, mute?)` | master volume 0-100 |
| `vibe.hw.power.off()` / `.reboot()` / `.suspend()` | power actions — only on explicit user click; the OS asks the user to confirm outside the app, declined → rejects with `cancelled: …` |

### WiFi connect — full reference

The WiFi API is how a kAIrOS app gets the machine online (NetworkManager underneath).
Every call is async and returns a plain object; nothing throws for missing hardware, and an
answer with `ok:false` carries `error` (a code) + `detail` (text) — the promise resolves with it.

**Discover the state**

```js
const s = await vibe.hw.wifi.status();
// { available:true, enabled:true, connected:true, ssid:"HomeNet", signal:72, bars:3, ip:"192.168.1.23",
//   connectivity:"full", device:"wlan0", devices:[{device,state,connection}] }
// available:false → no WiFi radio / NetworkManager (e.g. a desktop on ethernet or a VM)
// enabled:false   → the radio is off (vibe.hw.wifi.on()), or the laptop's hardware switch (reason)
// starting:true   → the WiFi chip is still starting after boot: show "starting…", poll again
// connectivity    → "full" online · "portal" a hotspot login page is in the way · "limited" / "none"
```

`ssid` is the network's real SSID (not the NetworkManager profile name), so it matches the
names in `scan()` and works for `forget()`.

**Scan for networks** (the list NetworkManager keeps — instant):

```js
const { networks, age_s } = await vibe.hw.wifi.scan();      // scan({fresh:true}) = a new radio scan (seconds)
// networks: [{ ssid:"HomeNet", signal:72, bars:3, band:"5", security:"WPA2 WPA3",
//              needs:"password", saved:true, in_use:true }, … ]
//   signal 0–100 / bars 0–4, already sorted strongest-first, one entry per network
//   needs  "none"     → open network or OWE ("Enhanced Open", e.g. Freifunk): connect without a password
//          "password" → WPA/WPA2/WPA3/WEP: ask for the password (a saved one is remembered)
//          "login"    → 802.1X / enterprise (user + certificate): not supported by this API
//   security "open" or nmcli's text ("WPA2", "WPA2 WPA3", "OWE-TM", …) — for display only
//   saved / in_use → a saved profile exists / the network you are on (badge it)
```

**Connect** — returns `{ok, error, detail, connectivity}`; NetworkManager also *saves* the
network so it reconnects automatically next boot. A wrong password never leaves a broken
profile behind, and a saved network's working password is kept when a new one is wrong:

```js
const r = await vibe.hw.wifi.connect("HomeNet", "the-user-typed-passphrase");
if (r.ok) {
  vibe.notify("online ✔");                       // r.connectivity "portal" → offer Sign in (below)
} else if (r.error === "wrong_password") {
  showFieldError("Wrong password");              // keep the password field open
} else {
  // needs_password · not_in_range · timeout · unsupported · failed — r.detail says more
  vibe.notify("couldn't connect: " + r.detail);
}
// open network or OWE (needs:"none"): await vibe.hw.wifi.connect("CoffeeShop")
// a saved network: await vibe.hw.wifi.connect("HomeNet") — uses the stored password
```

**Disconnect / forget / saved / radio**

```js
await vibe.hw.wifi.disconnect();          // {ok} — leave the network, keep the saved profile
await vibe.hw.wifi.forget("HomeNet");     // {ok, deleted} — delete every saved profile of that SSID
await vibe.hw.wifi.saved();               // {networks:[{ssid, auto, last_used}]}
await vibe.hw.wifi.off(); await vibe.hw.wifi.on();   // the radio; NetworkManager keeps it across reboots
```

**Hotspots with a login page** (trains, hotels, cafés): `status().connectivity` is `"portal"`
(NetworkManager's connectivity check, `/etc/NetworkManager/conf.d/20-kairos-connectivity.conf`).
`await vibe.hw.wifi.signin()` → `{ok, url, portal}` opens the login page in a real browser window
on the desktop; it closes by itself once the machine is online (Ctrl+W closes it too).

**The recommended connect flow for a WiFi manager app**

1. `status()` on open; if `available:false`, show "No WiFi on this machine" and stop; `enabled:false` → an on switch.
2. `scan()` → list networks (signal bars, 🔒 only for `needs:"password"`, badge `in_use`).
3. On tap: an open network (`needs:"none"`, also OWE) connects directly; a secured one shows an
   **inline** password field (never `window.prompt` — it is blocked in the kiosk) with a Connect button.
4. Call `connect(ssid, password)`, show a spinner, then re-`status()` to confirm.
5. On `ok:false`, surface `r.detail` (or a friendly text for `r.error`) and let the user retry.
6. `connectivity:"portal"` → a "Sign in" button calling `signin()`.
7. Poll `status()` every ~5 s so the header stays live (the answer is cached ~2 s, polling is cheap).

The `wifi-manager` programming-wiki recipe (`vibe.wiki("wifi-manager")`) has a ready
pattern the OS also injects automatically when you ask it to build a WiFi app.

### Bluetooth & airplane mode [R78]

```js
const bt = await vibe.hw.bluetooth.status();
// { available:true, powered:true, blocked:false, connected:["MX Master 2S"],          ← names
//   devices:[{ mac:"C0:FF:EE:00:00:01", name:"MX Master 2S", kind:"mouse", paired:true, trusted:true,
//              connected:true, battery:70 }], pairing?:{mac, state:"pairing"|"enter_code"|"paired"|"failed", code} }
await vibe.hw.bluetooth.scan();                 // {devices:[{mac, name, kind, rssi}]} — ~10 s ({seconds:5});
                                                //  only NEW devices seen in this scan (not paired, named)
const r = await vibe.hw.bluetooth.pair(mac);    // {ok, error, code, name, kind, trusted, connected, sound?}
await vibe.hw.bluetooth.connect(mac); await vibe.hw.bluetooth.disconnect(mac); await vibe.hw.bluetooth.remove(mac);
                                                // mac — or the device's exact name (one match)
await vibe.hw.bluetooth.off(); await vibe.hw.bluetooth.on();   // off = blocked, stays off after a reboot
```

- `kind`: `audio` (headphones, speakers), `mouse`, `keyboard`, `gamepad`, `phone`, `other`.
- `pair()` pairs, **trusts** (the device reconnects by itself after a reboot) and connects.
  Headphones become the sound output: `r.sound = {sink, default_by}` (`vibe.hw.sound` lists outputs).
- A keyboard: `r.error === "enter_code"` with `r.code` → show "Type 123456 on the keyboard, then
  Enter" and poll `status()` until `pairing.state` is `"paired"`. A phone shows `r.code` itself
  (it is confirmed automatically). Other codes: `auth_failed`, `not_in_range`, `timeout`, `busy`, `bad_mac`.
- `scan()` needs Bluetooth on (`powered:true`); it never switches it on by itself.

**Airplane mode** — both radios at once, kept across reboots (NetworkManager + rfkill):

```js
await vibe.hw.airplane.get();          // {available, airplane, wifi_enabled, bluetooth_blocked}
await vibe.hw.airplane.set(true);      // WiFi radio off + Bluetooth blocked; set(false) brings both back
```

## Image model setup

`vibe.models()` → the installed image models with their tuned defaults, which one is
active, and the user's overrides. **Defaults are deliberately good — only override to
experiment.** Configuration lives in normal settings keys:

| settings key | values | effect |
|---|---|---|
| `image_model` | `default` (Krea 2 (uncensored) — Krea 2 Turbo + the Kroma v0.3 LoRA, photoreal, no safety filter, ~80 s at 1024² on 8 GB, ~47 s per picture in a batch) · `safe` (Krea 2 (safe, faster) — the stock Krea 2, safety-tuned: clothes people, ~62 s / ~38 s) · `qwen` (Qwen-Image-2.1 — best text rendering, ~100 s) · `classic` (Z-Image-Turbo — fastest, ~27 s) · `uncensored` (= `default` since v7.5 [R76]) · `chroma` (Chroma1-HD — uncensored FLUX-family, slow, ~4 min) | which model renders `vibe.image()` / `vibe.images()` |
| `image_expand` | `auto` (default) · `on` · `off` | **prompt expansion**: before a Krea-family model (`default`, `safe`) renders, the OS rewrites the prompt with Krea's official expander rules (a paragraph with medium, light, composition; text in quotes kept) — by the coder LLM that is loaded anyway (`image_expander` below), no model swap. `auto` = on for the models that have an expander (`vibe.models()` → `models[].expander`), `off` = render prompts exactly as typed. Prompts the OS writes itself (the wallpaper scene, app icons, forge pictures) are never expanded a second time |
| `image_expander` | `auto` (default) · `llm` · `encoder` | [R79] **which model expands**: `llm` = the resident coder LLM (Gemma 4 on 8/16 GB, thinking off; `auto` = this unless the model's section says otherwise), `encoder` = the image model's own Qwen3-VL-4B text encoder under llama-server (the v7.5 way: one extra model load per picture on an 8 GB GPU). `vibe.models()` → `expand.expander.effective` |
| `image_steps` | number or null | diffusion steps (null = model default) |
| `image_sampler` | e.g. `euler`, `er_sde`, `dpm++2m` | sampling method |
| `image_scheduler` | e.g. `simple`, `beta`, `karras` | sigma scheduler |
| `image_cfg` | number or null | guidance scale |

Example: `await vibe.settings.set("image_model", "qwen")` — a per-call override is also
possible: `POST /api/image {"prompt", "model": "qwen"}`; likewise `"expand": false` renders
the prompt verbatim for one call, `"adult": true` picks the expander's 18+ rules. Requested
resolutions are auto-fitted to the model's VRAM budget (aspect kept, snapped to 64).

Only Krea 2 is baked into the shipped OS — as the **default** (with the Kroma v0.3 LoRA,
uncensored) and as **safe** (the same files without the LoRA); `qwen`, `classic`
and `chroma` are **add-ons** — `vibe.models()` reports them with `addon:true,
present:false, download_gb` (and `licence` where one applies: Qwen-Image-2.1 is under the
Qwen Research licence). Fetch one with `await vibe.models.download("qwen")`
(background; poll `vibe.models()` for `present`). Choosing an add-on that isn't
downloaded yet transparently falls back to the default. Bigger model **tiers**
(16/24/32 GB) download via `vibe.system.upgrade(tier)` — see `vibe.system.setup()`.

### Several pictures in one run — `vibe.images()` / `POST /api/images`

Loading an image model costs ~10 s of every picture on an 8 GB card. `vibe.images()` keeps
the model loaded for a whole list (the kernel runs one `sd-server` session; where the engine
set has no server, pictures are rendered one by one with the same result):

```js
const urls = await vibe.images(["a red fox at dawn", "the same fox at noon", "the fox at dusk"]);
const four = await vibe.images("abstract neon wallpaper", 4);                 // 4 variations, fresh seeds
const wide = await vibe.images(["hero shot", "footer art"], { width: 1024, height: 576, model: "classic" });
```
`POST /api/images {"prompts": [...]}` or `{"prompt", "count"}` (+ `model`, `width`, `height`,
`adult`, `expand`) → `{"job", "count"}`; poll `/api/job/{id}`: `result` = the URLs in prompt
order (`null` where a picture failed), `results` = per-picture records (`prompt` as rendered,
`expanded`, `seed`, `error`). The job is `done` when at least one picture rendered. Pictures
written as `<img src="/genimg/…">` on one page are batched the same way automatically.

## System settings

Settings live in `/data/settings.json` (so a format() factory-resets them too).
Apps may read **and change** them; the OS applies changes live within seconds.

| call | effect |
|---|---|
| `vibe.settings.get()` | full settings object |
| `vibe.settings.get(key)` | one value |
| `vibe.settings.set(key, value)` | change a setting (any app may) |

Known keys: `wallpaper` (image URL or null), `accent` (CSS colour, default `#7c5cff`),
`accent2` (CSS colour, default `#41e2ff`), `os_name` (1–40 characters, shown in the menu bar),
`image_model`, `image_expand`, `image_expander`, `image_steps`/`image_sampler`/`image_scheduler`/`image_cfg`
(image model setup above), `llm_model` (the coder LLM, below) and `translation`/`language`/
`translation_quality` (the translation layer, below). **Known keys are
validated**: a wrong type or value (a non-colour accent, `image_expand: "maybe"`, a missing
value) is rejected — `POST /api/settings` answers `400 {"error": <the rule>, "key"}` and the
bridge promise rejects with that message; nothing is stored. Unknown keys are allowed (≤ 64 KB
of JSON each) — use them as a system-wide preference store.

### The coder LLM — default brain or fast mode

The OS writes apps, pages and games with its coder LLM. On the 8 GB and 16 GB tiers the
default is **Gemma 4 26B-A4B-it** (the only model whose generated apps passed the feature
test: 36/37 functional items; 3–5 min per app on an 8 GB card). **Fast mode** switches to the
small **Qwen2.5-Coder-7B** (≈ 40 s per app, simpler and less reliable results), a
downloadable add-on (4.7 GB):

| settings key | values | effect |
|---|---|---|
| `llm_model` | `default` (the tier's brain) · `fast` (the `llm_fast` add-on) · `uncensored` (the `llm_uncensored` add-on [R86]) | which model answers `vibe.ask()`, writes apps (`/api/app`), pages (`/web/…`) and games. The kernel restarts its language model on the next request after a change. A `fast` / `uncensored` choice whose add-on is not downloaded keeps serving the default — `vibe.models()` → `llm_setting.fallback` says so |

`vibe.models()` → `llm: [{key: "default"|"fast"|"uncensored", name, present, addon, download_gb,
download_key, downloading, selected, active}]` + `llm_setting: {setting, effective, fallback, modes}`;
`vibe.models.download(entry.download_key)` fetches an add-on — `"fast"` for the fast coder,
`"llm_uncensored"` for the decensored LLM (the bare key `"uncensored"` names the baked image model, see
*Uncensored image model*); `GET /api/status` → `llm` (the effective
model's name) and `llm_options`. [R80] `GET /api/status` → `gpu: {kind, key, name, full_name, since, loading}` =
what is resident on the GPU right now (`kind` llm | llm_fast | llm_uncensored | expander | vision | translation |
image | video | music | none; `name` as the menubar shows it, e.g. "Gemma 4 26B-A4B-it", "Krea 2 · Kroma"; an
image session keeps it through its 8-s idle window).

**The refusal fallback [R86]** (`docs/REFUSAL-FALLBACK-2026-10-09.md`): when the LLM declines a request
("I cannot fulfill this request…") instead of answering, the kernel never returns or caches the refusal. It
retries on the ladder of the tier manifest's `refusal_fallback.ladder` — `preamble` (the same model with the
18+ system preamble, no swap), then `llm_uncensored` (the decensored add-on, swapped in like `fast`, back on
the next request; skipped while not downloaded) — and only when every rung declined does the request fail
with a plain error: `vibe.ask()` rejects / `POST /api/ask` → `502 {"error": "the model declined this request
… vibe.models.download('llm_uncensored')"}`, `/web/…` shows its error page (nothing cached), `/api/browse`
→ `502 {"error", "address"}`, `/api/app` sends `event: error`. While an app streams, a refusal restarts the
generation on the next rung and the stream carries `event: refusal` `data: {from, to, to_name, reason, kind,
message}` (the shell resets its code view and toasts the message) — before the real app's `delta`s, or, when
the refusal only shows at the end of a document, after them (round 2: the whole stream is judged again); the
app's spec step reports its own climb the same way, and the rung that answered then serves the whole summon
(the stream, every repair round) without restarting at the model that declined. A refusal that itself names
minors ends the ladder with the minors guard's 400 / `error` instead.
`GET /api/status` → `last_fallback: {at, from, to, kind, reason, prompt}` (null until one happened) and
`refusal_fallback: {ladder, expander_ladder, uncensored: {available, reason, section, download_key}, count,
blocked, last}`; `vibe.models()` carries `refusal_fallback` too. The image-prompt expander has its own cheap
rungs (`expander_ladder`: the same LLM with the 18+ preamble, then the image model's own encoder with the 18+
rules); when every rung refuses, the picture is declined (`/api/image` job `error: "the prompt writer declined
this picture …"`, `/api/images` result `declined: true`) — the raw prompt renders only on an engine error.
**The minors guard** runs before any of this: a request that pairs a sexual term with a minor /
childlike indicator fails at once — `400 {"error": "kAIrOS does not create sexual content involving minors
or childlike characters"}` on `/api/ask`, `/api/image`, `/api/images`, `/api/game`, `/api/browse`,
`/api/app/{id}/modify`, `/api/vision`, `/api/video`, `/api/music` (caption or lyrics), `/api/search`;
`/api/app` → `event: error`; `/genimg/…` → an SVG placeholder ("not rendered"); `/web/…` → the error page —
nothing is generated, rendered or cached. With the translation layer on, the request's English is guarded
too; a list of content parts or any JSON is judged as its text. Content cached before the guard knew the form
is hidden — not in `vibe.apps()` or `/api/status`, `/app/{id}` → 403, a cached page not served — and moved to
`cache/quarantine/` (with its icon) only when the owner summons that prompt again; a `/genimg` picture of a
blocked description is quarantined on the request.
`vibe.models.download("uncensored")` stays the (baked) image model; `POST /api/models/download {"model":
"uncensored", "kind": "llm"}` means the LLM add-on (= `download_key` `llm_uncensored`).

### Language & translation — the OS speaks your language [R71]

Off by default: nothing is translated and no model runs. Switched on with a `language` other
than English, the OS translates its own UI (menu bar, dock, dialogs, every app window) through a
local machine-translation model, its coder LLM writes apps, pages, games and `vibe.ask()` answers
in that language, and what the English-only models need (image/video/music prompts, knowledge
searches) is turned into English on the way. Languages: `en de es fr it ja ru`.

| settings key | values | effect |
|---|---|---|
| `translation` | `off` (default) · `on` | the switch. Off = zero change: no model started, prompts untouched, nothing in the DOM |
| `language` | `en` (default) · `de` · `es` · `fr` · `it` · `ja` · `ru` | the user's language; `en` with translation on = nothing to translate |
| `translation_quality` | `fast` (default) · `quality` | `fast` = the 2B model on the CPU (its own server: never evicts the GPU model, starts on first use, stops when switched off) · `quality` = the 9B model on the GPU (takes the coder LLM's slot like vision; falls back to `fast` while its file is missing) |

The models are the `translation` add-on. The fast 2B is **built into the shipped OS** (image
v7.3+), the quality 9B is the optional download: `vibe.models()` → `extras[translation]` =
`{present, present_modes: {fast, quality}, missing_gb, download_gb, available, downloading}` —
`present` is true as soon as the layer can translate (one of the two files is there: the baked
fast one), `present_modes` says which file is on disk, `missing_gb` what
`vibe.models.download("translation")` still fetches (the 9B: 5.8 GB on the 8 GB tier; 0 when
both are there) and `download_gb` the whole add-on (7.1 GB). A settings app shows translation as
installed while `present` is true and offers the quality model while `present_modes.quality` is
false. `vibe.models()` → `translation` = `{enabled, language, languages, names, quality,
effective, fallback, present: {fast, quality}, running, cache}` (its `present` is the per-file
object, the same as `present_modes`). API: `POST /api/translate` — body `{"text": "…"}`
or `{"texts": ["…", …]}` (≤ 200 texts, ≤ 4000 chars each) + optional `to` / `from` (language
codes; `to` defaults to `language`) → `{"text" | "texts", to, from, model, calls, cached, ms}`.
Repeats come from a persistent per-language cache (no model call). `400 {"error"}` while
translation is off (the message names the setting) or the add-on is missing (it names the
download). `GET /api/translate/status` (and `GET /api/status` → `translation`) → the object above.
Bridge: `await vibe.translate(text)` → string in the OS language, `await vibe.translate([a, b])`
→ array, `vibe.translate(text, "en")` into a named language. A settings app renders a language
picker from `translation.languages` / `names`, an on/off switch and the fast/quality choice with
`vibe.settings.set("translation" | "language" | "translation_quality", value)`. The desktop's and
the apps' own UI texts always go through the `fast` model (a UI batch never swaps the GPU model
out); `translation_quality: quality` applies to explicit `vibe.translate()` calls.

### Dictionaries & Wiktionary — look words up, offline [R71 P3]

`vibe.dict(word, from?, to?)` → `GET /api/dict?word=&from=&to=&limit=` → `{word, from, to,
entries: [{headword, display, pos, translations: [...], source, from, to, match}], count, limit,
matches: {exact, folded, prefix}, sources: [{id, label, from, to, entries}], errors, ms}`. The
dictionaries are the `dictionaries` add-on (118 MB: TU Chemnitz BEOLINGUS de↔en, GPL, plus 37
FreeDict pairs among en/de/es/fr/it/ja/ru, GPL / CC-BY-SA — `vibe.models()` → `extras[dictionaries]`
with `pairs`, `vibe.models.download("dictionaries")`); the kernel indexes them on first use. Matches
come exact first ("Haus"), then case/diacritic-folded ("haus", "HAUS"), then by prefix ("Hau" →
"Hau ab!"), capped at `limit` (default 20, ≤ 50). `to` defaults to the OS `language`; without
`from`, every dictionary INTO `to` answers and each entry names its `from`. It works whether
translation is on or off. `400 {"error"}`: no word / a bad code / `from == to` / no dictionary for
the pair (es↔ja has none; the message lists the pairs) / the add-on missing (names the download).
`GET /api/dict/status` → every dictionary with `present`, `indexed`, `entries`, `licence`.

The Wiktionaries are knowledge add-ons: `wiktionary_en`, `wiktionary_de`, `wiktionary_es`,
`wiktionary_fr`, `wiktionary_it`, `wiktionary_ja`, `wiktionary_ru` (one ZIM per language, 0.4–9.2 GB,
CC-BY-SA; `vibe.models()` → `extras[wiktionary_<lang>]` with `language`, `present`, `download_gb`,
`serving`; `vibe.models.download("wiktionary_de")` — pick yours + English). Once downloaded they are
served next to Wikipedia: `vibe.search()` consults every installed ZIM (Wikipedia and the English
Wiktionary with the English query, the Wiktionary of the OS language with the words as typed when
translation is on) and each hit says its `source` ("Wikipedia (en)", "Wiktionary (de)"); a Wiktionary
answers the page whose title is the query first. `vibe.ask()`, apps and pages are grounded the same
way (the facts name their book). Hits from the OS language's Wiktionary are not re-translated.

## Living software

Your code is temporary: each version of an app runs exactly once. When the user
relaunches you, the OS feeds your current code back to the model to build the next
version — so **keep your `vibe.store` keys stable** across versions; they are the part
of you that survives. Old versions remain on disk under the app's `history/`.
Image/video generations always use a fresh random seed — results are never repeated.

## Rules of the road

- Apps are sandboxed iframes: no network, no parent DOM. The bridge is the only door.
- **No native dialogs**: `window.alert()`, `window.confirm()` and `window.prompt()` are
  blocked by the sandbox — the OS shims them into a non-blocking notice, `confirm()` answers
  `false`, `prompt()` answers `null`; a document that calls `prompt()`/`confirm()` is sent back
  to repair before delivery. Ask, confirm and collect text with in-page elements
  (an `<input>` + button, an overlay `<div>` with Yes/No).
- `vibe.ask()` is the OS **language model**, never a way to ask the user: file names, titles
  and choices come from in-page inputs.
- **Only documented members exist**: an unknown `vibe.*` member is `undefined`
  (`typeof vibe.hw.haptics === "undefined"`, `"haptics" in vibe.hw === false`) and the
  console names the real API — feature-detect with `typeof vibe.vision === "function"` and skip
  what is missing; never invent calls.
- Destructive or expensive calls — `vibe.fs.format()`, `vibe.system.upgrade()`,
  `vibe.hw.power.*` — are confirmed by the OS in its own dialog; declined → the promise
  rejects with `cancelled: …`.
- Runtime errors are watched by the OS — crash and you'll be self-healed (regenerated), at
  most three automatic rounds per version; then the window shows the error and offers a
  manual repair / ✨ improve.
- Every inline `<script>` is parsed by the OS before an app is delivered (a real JavaScript
  parser); a script that does not parse is repaired at generation time. If two repair rounds
  cannot fix it, the app is still delivered — flagged: the stream's `done` (and `cached`/
  `fallback`, the repair reply, the `/app/<id>` page) carries `broken: {message, line, problems,
  rounds}`; the window shows the parser message at once and does NOT start the automatic
  self-heal on it (✨ improve or "repair once more" instead).
- The dialog check reads only executable code (inline scripts and `on*=` handlers, strings and
  comments stripped): text such as `placeholder="Describe your image prompt (e.g. a fox)"`
  never triggers a repair round; a global `prompt()`/`confirm()` call does.
- The OS confirmation's OK button is disabled for the first 0.7 s (countdown in its label): a
  click that was already on its way cannot consent.
- Look modern and futuristic: dark glass, neon violet/cyan, rounded, smooth.

## Music generation

`POST /api/music` — body `{"prompt": "dreamy synthwave", "lyrics": "optional", "duration": 60,
"language": "en"}` → `{"job": id}`; poll `/api/job/{id}` → `result` is the audio URL under
`/files/music/`. `language` = ISO 639-1 code of the sung lyrics; **default `"en"`**, `"auto"`
lets the model guess, an unknown code is `400 {"error", "accepted": [...]}` with no job.
Returns `400 {"error"}` (no job) when the acestep.cpp engine is not installed or the
music add-on is not downloaded (`/api/models` → `extras[music].engine/available`).
Bridge: `await vibe.music(prompt, lyrics, duration, language)` → audio URL, e.g.
`vibe.music("Schlager, Akkordeon", "[Verse]\nIch tanze durch die Nacht", 30, "de")`. Local
ACE-Step model; lyrics empty = instrumental (language ignored). Duration capped at 240 s.
The music model is a downloadable add-on: `try/catch` it and keep the app usable without it.

## Vision — the OS looks at pictures [R70]

`POST /api/vision` — body `{"image": …, "prompt": "What is this?", "max_tokens": 512}` →
`{"text": "…"}` directly (like `/api/ask`: an answer, no job to poll). `image` is one of:
a `data:image/<type>;base64,…` URL (≤ 6 MB decoded — a canvas `toDataURL()`, a photo), a
kernel-served path (`/files/images/x.png`, `/genimg/<desc>` once rendered — resolved inside
the media cache only; anything else is `400`, a missing file `404`), or `"screen"` /
`"screen:N"` (the kiosk display: every monitor as laid out, or monitor N in the `?screen=N`
numbering). Pictures are fitted to 1280 px (aspect kept, never upscaled) before the model
sees them, so a phone photo cannot overflow the context. The model is the Qwen3-VL add-on —
the image model's text encoder plus its `mmproj` projector under `llama-server`; it takes the
LLM's GPU slot for the call and the coder LLM reloads on the next LLM request. `400
{"error"}` when the add-on is not downloaded (`/api/models` → `extras[vision]`,
`vibe.models.download("vision")`, 0.45 GB). Bridge: `await vibe.vision(image, prompt)` → string.
`"screen"` is the one source that needs trust (see below): it shows what the user is looking at.

## Uncensored image model

Since v7.5 [R76] the **default** image model is uncensored: Krea 2 Turbo + the Kroma v0.3 LoRA
(lodestones' Krea 2 fine-tune without the safety tuning, applied at runtime — same look, text
intact). Its prompt expander keeps people exactly as requested (no clothing added over requested
nudity, no nudity nobody asked for; whenever nudity or sex is requested every person is an adult
of 25+, never minors, never real people). `"uncensored": true` (and `image_model` `uncensored`)
now simply means the default, with the expander's 18+ rules for that call; `model: "safe"` /
`image_model` `safe` is the stock, safety-tuned Krea 2 (≈ 20 % faster). The job record says which
LoRA was applied (`lora`, null = stock). Chroma1-HD stays reachable as `model: "chroma"`
(uncensored FLUX family, ~4× slower). Same job flow as normal images.

## HTTP access from outside the kiosk (operators, curl) — the trust boundary [R66]

`window.vibe` needs none of this: apps talk to the shell, the shell talks to the kernel
on loopback. For anyone else:

- The kernel listens on `127.0.0.1:1337` unless `VIBEOS_HOST=0.0.0.0` was set for
  `kairos.service` (a drop-in — deliberate, for hardware-test monitoring).
- Read-only routes (`GET /api/status` — incl. `llm_options` and `js_gate`, `/api/hw`, `/api/models`, `/api/install/status`,
  `/api/job/{id}`, docs, wiki…) and the generation routes (`/api/app`, `/api/image`,
  `/api/video`, `/api/music`, `/api/vision`, `/api/ask`, `/api/browse`, `/genimg/…`, `/web/…`) answer any
  peer — except `/api/vision` with `"image": "screen"`, which reads the user's display [R70]
  and is treated like the machine-changing routes below.
- Routes that change the machine (`/api/install`, `POST /api/hw` other than status/scan/
  list/get/timezones, `/api/fs` write/mkdir/delete/format, `POST /api/settings`,
  `/api/wallpaper`, `/api/store`, `/api/models/download`, `/api/setup/upgrade`,
  `/api/setup/done`, `/api/game`) answer **403** to a
  non-loopback peer unless the request carries `X-Kairos-Token: <this boot's token>` —
  the token is in `/run/kairos/token` on the machine (root, or the kiosk user).
- `GET /api/token` hands the token to loopback callers only; the shell uses it, and an
  operator can open `http://<ip>:1337/?token=<value>` to get a fully working remote desktop.

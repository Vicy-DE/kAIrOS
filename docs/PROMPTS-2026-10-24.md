## 1. Where the prompts were, and where they are now

Before this round the prompts were Python constants in `kernel/prompts.py` (plus `TRANSLATE_PROMPT` in `server.py` and
the dock apps' forge requests as `data-prompt` attributes in `shell/index.html`), readable only in the source; two of
them were copied to the VFS as `/system/prompts/app_system.txt` and `game_system.txt`. Changing one meant editing the
code and restarting the kernel (on the stick: a new image).

Now every prompt has one name, one shipped default, one line and one note, and can be read and edited in four places
that all mean the same thing:

| place | what | how |
|---|---|---|
| `kernel/prompts.py` | the shipped defaults + **the registry** at the end: `DEFAULTS`, `WHERE` (file:line, read from the module's own AST), `NOTES` (who sends it), `_DERIVED` (compositions), `kind_of` / `editable`, `load_overrides`, `set_override`, `clear_override`, `register` (external prompts), `on_change` | the permanent change: edit, or `prompt-sync.py bake` |
| `KAIROS_PROMPTS_DIR/<NAME>.txt` (default `$VIBEOS_DIR/prompts`; `/opt/vibeos/prompts` on the stick) | **the overrides** of a running system: read at start, before anything copies a prompt value | the ✎ Prompts panel, `/api/prompts`, `prompt-sync.py push` |
| `GET/POST /api/prompts[/<name>]` | the registry over HTTP: list (+`?full=1`), one prompt with its default, `{text}` / `{reset: true}` / `{reload: true}`; guarded like every machine-changing route | the panel and the script |
| `/system/prompts/<NAME>.txt` (VFS) | read-only copies of the live values for apps, refreshed on every change (the two legacy names stay) | `vibe.fs.read` |

54 prompts are registered on the 8 GB tree: 50 from `kernel/prompts.py` (33 editable, 17 parts / legacy) + 4 dock
prompts (`DOCK_SETTINGS`, `DOCK_NOTES`, `DOCK_NEWS`, `DOCK_FILES`). The complete catalogue with every text, its line
and who sends it is the generated document (§5), and `prompt-sync.py list`.

**Kinds.** `system` (sent as the system message: APP_SYSTEM, APP_REGEN_SYSTEM, APP_EVOLVE_SYSTEM, HTML_FIX_SYSTEM,
GAME_SYSTEM, GAME_FIX_SYSTEM, ASK_SYSTEM, VISION_SYSTEM, BROWSER_SYSTEM, WEB_EVOLVE_SYSTEM, SPEC_SYSTEM, the three
KREA_EXPAND_SYSTEM*, LYRICS_SYSTEM, WALLPAPER_SYSTEM), `instruction` (appended / prepended texts: APP_ASSETS_INSTRUCTION,
the GAME_EVOLVE_* texts, WIKI_HEADER, API_HEADER, KREA_EXPAND_ENGLISH, ADULT_PREAMBLE, UNCENSORED_LIMITS), `template`
(formatted at use: CONTEXT_HEADER, WEB_EVOLVE_SITE_INTRO, LANGUAGE_INSTRUCTION, TRANSLATE_PROMPT), `hint` (media
suffixes: IMAGE/VIDEO/MUSIC_PROMPT_HINT, WALLPAPER_PROMPT), `dock` (the forge requests), `part` (STYLE, the ADULT_*
rules, the _KREA_* rules, the _*_TAIL texts — baked into the prompts built from them, therefore read-only: edit the
finished prompt), `legacy` (BROWSER_NAV_SCRIPT, stripped from old cached pages, never sent).

**What changed in `kernel/prompts.py`.** The three compositions became `base + part` with named parts
(`_APP_REGEN_TAIL`, `_APP_EVOLVE_TAIL`, `_WEB_EVOLVE_TAIL`) so an override of `APP_SYSTEM` rebuilds `APP_REGEN_SYSTEM`
and `APP_EVOLVE_SYSTEM` (unless those are overridden themselves); `TRANSLATE_PROMPT` moved in from server.py; the
songwriter's `LYRICS_SYSTEM` is new. Every shipped value is byte-identical to before (checked against the backup;
`pr_registry_complete`).

**What changed in `kernel/server.py`.** `PROMPTS_DIR` + `prompts.load_overrides()` right after the path constants
(before `EXPANDERS` and `LANGUAGE_PROMPTS` copy values); `register_dock_prompts()` reads `shell/index.html`;
`dock_prompt()` substitutes an override in `_app_generate` (logged); `prompts_apply()` on every change refreshes
`EXPANDERS`, `LANGUAGE_PROMPTS`, `TRANSLATE_PROMPT` and `FS.populate_system(prompt_system_files())`; the routes
`GET /api/prompts`, `GET /api/prompts/{name}`, `POST /api/prompts/{name}` (guarded), `POST /api/prompts` (guarded,
reload); `main()` populates every prompt into `/system/prompts/`.

**The dock prompts** are the one case where an override does not apply to the next request by itself: a dock app that
already has a cached version keeps running it (living software: the prompt is saved in its `meta.json` for ✨ improve).
The override is used when the app is generated anew — remove its cache entry (`cache/apps/<app_id>/`) or forge it fresh.
The panel's note says so.

## 2. The ✎ Prompts panel (the tool in the OS)

`shell/prompts.js` — the OS's own panel, like Models & licences: a list by kind with an "edited" badge and the size,
the chosen prompt's name, kind, location and note, the live text in an editor, **Save** (Ctrl+S; the kernel writes the
file and the next generation uses it), **Reset to default**, **Show default** (compare), **Copy**; a footer with the
count, the override directory and the sampler fields (songwriter, LLM vendor, expander). Parts are shown read-only with
the hint to edit the prompt built from them. Opened from ⊞ Apps → Prompts, About kAIrOS → Prompts, the desktop search's
system apps, `openStudio("prompts")`. Every server string is set as text or `.value`, never as HTML.

## 3. `scripts/prompt-sync.py` (the script)

A folder of `<NAME>.txt` files is the exchange format; `INDEX.md` next to them lists name, kind, location, size, state
and note.

```
scripts/prompt-sync.py list   [--kernel URL]                    every prompt (the repo's defaults, or a kernel's live state)
scripts/prompt-sync.py export DIR [--kernel URL]                <NAME>.txt for every prompt + INDEX.md
scripts/prompt-sync.py diff   DIR [--kernel URL] [--full]       which files differ from the shipped defaults
scripts/prompt-sync.py push   DIR --kernel URL | --dir OVR      the differing files become overrides (live, or copied)
scripts/prompt-sync.py pull   --kernel URL | --dir OVR  DIR     the overrides back into a folder
scripts/prompt-sync.py reset  NAME… | --all  (--kernel | --dir)
scripts/prompt-sync.py bake   DIR [--only A,B] [--check]        the texts become the shipped defaults (kernel/prompts.py,
                                                                shell/index.html for DOCK_*); backup under
                                                                $KAIROS_HOME/repo-backups/<date>/, verified by re-import
scripts/prompt-sync.py html   [-o FILE] [--kernel URL] [--fragment]   the architecture + prompts document
```

Rules the script keeps: a file equal to the shipped default is never an override (push removes a stale one, on the
kernel and in a directory); an editor's trailing newline is not part of a prompt whose default has none; parts are
skipped with a message; `bake` keeps an f-string's interpolations (`{STYLE}`, `{ADULT_RULE_APP_SHORT}`, …) wherever the
part's current value occurs in the new text, escapes quotes / backslashes / triple quotes, refuses a composition (bake
its base or its part instead), writes the dock attribute HTML-escaped, and restores the backup when the re-import does
not reproduce every value. Baked literals are one long triple-quoted string per prompt (the source's `\` line
continuations are not recreated).

## 4. The songwriter (R93): Melody's lyrics box is a prompt box

`POST /api/lyrics` (`vibe.lyrics(brief, opts)`): the loaded LLM gets `prompts.LYRICS_SYSTEM` and one user message
(`SONG: <the brief>`, plus `MUSIC STYLE:`, `LENGTH:`, `LANGUAGE:`, `BPM:`, `KEY:`, `TIME SIGNATURE:` lines when the
caller pins them) and answers ONE JSON object — `title, caption, lyrics, language, duration, bpm, keyscale,
timesignature` — pinned by llama-server's `json_schema` grammar (`LYRICS_SCHEMA`). Sampling is the owner's:
`LYRICS_SAMPLING = {"temperature": 1.2, "top_k": 80}`, passed as the per-call override that `chat_payload` merges last
(above the LLM section's vendor sampling), so these two fields reach llama-server whatever the manifest says
(`pr_lyrics_route` reads them off the mock's wire log). `max_tokens` 2400.

The rules in the prompt are ACE-Step 1.5's (docs/MUSIC-FIXES-2026-10-23.md §4; the 150-song batch of 2026-10-23 used
the same recipe with Gemma and json_schema: 150/150 songs, 28 of 178 attempts failed the tag check at temperature 1.0):
tags only, no BPM / key in the caption, 6–10 syllables, (backing vocals), UPPERCASE = shouting, no repeat markers,
~45 words per minute, the length from the brief's form (jingle 20–40 s … epic 300–420 s), the language of the brief.

`lyrics_check` makes the answer safe for the engine whatever the model did: `music_caption_check` lifts BPM / key /
time signature out of the caption; `music_lyrics_check` drops `x2` / `(repeat)` markers; `lyrics_tag_fix` maps aliases
(`[Hook]` → `[Chorus]`, `[Solo]` → `[Guitar Solo]`, `[Refrain]` → `[Chorus]`, …), keeps a verse / chorus number, cuts a
descriptor to one short one (`[Bridge - soft, with piano and rain sounds]` → `[Bridge - soft]`) and DROPS a bracket
line that is no tag (the singer would sing it) — every change is listed in `fixes`; `duration` is clamped to
20..512 s, `bpm` / `keyscale` / `timesignature` go through `music_meta`, the language through `music_language` (an
unknown one becomes `en`); fewer than four sung lines, no caption or no JSON = a broken song → asked again, 3 attempts,
then `502`. The caller's fields win over the plan. The minors block runs on the brief at the entry and on the written
lyrics before they are returned; a refusal answers 422 like `/api/ask`.

**Melody** (`shell/shell.js` STUDIO.melody): the style input on top (empty = the songwriter's caption is taken), the
big box below is the prompt box — "the song in your words — a theme, a story, a mood, maybe a length" — with
**✍ Write lyrics** (the lyrics replace the text, the plan fields length / bpm / key / time and the title fill in,
all editable) and **Compose** (writes the lyrics first when the box holds no tagged text, then `vibe.music(style,
lyrics, length, language, {bpm, keyscale, timesignature})`). A pasted text with a `[Verse]` / `[Chorus]` line is sung as
written; an empty box is a 60 s instrumental as before. The bridge gained `vibe.lyrics(brief, opts)` (shell.js and
host.js in parity); `docs/API.md` and `docs/api/media.md` document it for the coder LLM.

**A finding on the way (recorded in the HTML document's Sampling section).** `chat_payload` merges the LLM section's
`sampling` into every request after the route's own `temperature`; the 8/16 GB manifests ship Gemma with
`temperature 1.0` in that block, so every Gemma generation (apps, pages, ask, games, repairs) effectively runs at 1.0
whatever the route asked for (0.4 for a repair, 0.75 for an app …). Only the translation hop (`vendor_sampling=False`)
and the songwriter (the per-call override) escape it. Not changed in this round (a manifest decision for the owner:
remove `temperature` from `llm.sampling` to make the per-route values count).

# Fixes 2026-10-22 — X without DNS, the grey boot frame, quality translation without a GPU

Three small fixes the owner ticked on 2026-10-21, found by the v7.5-3 image's verification (the two-monitor VM run and
the GPU-off boot). They go into the next images (the v7.5-3 public images, the owner's next card image).

Every number below was measured in the VM rig of the v7.5-3 build: QEMU with KVM and OVMF, 8 GB, **no GPU**, one
virtio-vga device with two heads (1920×1080 + 2560×1440), SLIRP `restrict=on` (offline; its DHCP gives no DNS server
and the guest's DNS packets are dropped), a **fresh qcow2 overlay** of the flat v7.5-3 media image per run. "Before" =
the image as shipped; "after" = the same image with this tree synced in by `dev/rig/testrig/sync-guest.sh` (no engines,
no apt) and rebooted.

## 1. X waited 40 s on DNS for the hostname

**Cause (measured).**
- The image's `/etc/hosts` is **empty** (0 B): live-build blanks it at the end of the ISO build and `build-img.sh`
  purges live-config, which used to write it at boot. `/etc/hostname` = `localhost.localdomain`; nsswitch `hosts:
  files dns`.
- `/etc/resolv.conf` is a **regular file baked into the image**: `# Generated by NetworkManager` / `nameserver 10.0.2.3`
  (mtime 2026-10-07 — QEMU's user-net DNS, written by NetworkManager in a build or test VM).
- startx takes the hostname with `uname -n` (no lookup) and then runs `xauth list localhost.localdomain:0` and `xauth add
  …` — xauth resolves the name. With nothing in `/etc/hosts` the resolver asked 10.0.2.3; the rig drops that, so every
  lookup took **20.0 s**. Two lookups = X 40 s late. Even `localhost` went to DNS:
  `getent ahosts localhost` and Python's `getaddrinfo("localhost")` also took 20.0 s.
- The laptop (stick log 2026-10-16) did not wait — no route at that moment, the lookup failed at once — but its x.log
  shows the same failed lookup: `xauth: bad display name "localhost.localdomain:0" in "add" command`.

**Does the baked resolv.conf break DNS on real networks?** Mostly not, but it is wrong. NetworkManager 1.52 runs with
`dns=default`, `rc-manager=symlink (auto)`, no systemd-resolved, no resolvconf. Measured in the guest (a DNS server
applied to the connection at runtime, `nmcli device modify`): NetworkManager then writes `/run/NetworkManager/resolv.conf`
**and** the regular `/etc/resolv.conf`; with no DNS server it rewrites `/etc/resolv.conf` without one. On a network
whose DHCP hands out DNS the baked file is therefore replaced at the first connect. Until then (the boot, before WiFi
joins) and on a network that gives no DNS server, every lookup goes to 10.0.2.3: it fails at once without a route and
waits 5 s per attempt with one. Each booted image also writes its network's resolver back into `/etc` — which is how
10.0.2.3 got into the image.

**NetworkManager's hostname.** NetworkManager treats `localhost.localdomain` as "no hostname" and, by default, takes one
from DHCP or a reverse-DNS lookup of the address (the stick log shows it looking on every device change). A changed
hostname is no longer in `/etc/hosts`, and X clients look their cookie up by the current hostname — startx wrote it
under the old one.

**Change.**
- `iso/config/includes.chroot/etc/hosts` (new): `127.0.0.1 localhost`, `127.0.1.1 localhost.localdomain` (the Debian
  line for the hostname — `scripts/public-image-prep.sh` already renames it to `kairos` on public images) and the IPv6
  lines.
- `etc/tmpfiles.d/kairos.conf`: `L+ /etc/resolv.conf - - - - /run/NetworkManager/resolv.conf` — at every boot, before
  NetworkManager, `/etc/resolv.conf` becomes the link to NetworkManager's runtime file (tmpfs). Until NetworkManager
  writes it the link dangles: glibc asks the local host, where nothing answers, and a lookup fails at once.
- `etc/NetworkManager/conf.d/20-kairos-dns.conf` (new): `rc-manager=symlink` (what "auto" chose, now written down) and
  `hostname-mode=none` (the hostname stays the one `/etc/hosts` names).
- `iso/build-img.sh`: a "names" step after the chroot step (live-build's own `chroot_hosts` / `chroot_resolv` steps
  rewrite both files at the end of the ISO build): installs the three files, points the `127.0.1.1` line at the image's
  `/etc/hostname`, replaces `/etc/resolv.conf` with the link, and fails the build if either is wrong.
- `scripts/public-image-prep.sh`: verify fails on a `/etc/resolv.conf` that is not the link and on an `/etc/hosts`
  without a `127.0.1.1` line; prepare fixes both (adds `127.0.1.1 kairos`, links resolv.conf).
- `.xinitrc` / `.bash_profile` / startx: checked — no other name is looked up (`:0`, `uname -n`, and `localhost`, which
  curl and Chromium resolve themselves; now also in `/etc/hosts`).

**Proof (VM, the rig that drops DNS).**

| | before (v7.5-3 as shipped) | after (this tree) |
|---|---|---|
| X attempt 1 (uptime) | 6.16 s | 6.35 s |
| Xorg log opened | +40 s | the same second |
| `.xinitrc` started | 47.00 s | 7.12 s |
| desktop ready (bootlog) | 49.2 s (48.9 s on run 2's first boot) | 8.3 s |
| `getent ahosts localhost.localdomain` | 20.03 s, fails | 0.00 s → 127.0.1.1 |

## 2. The grey frame at the boot → desktop handover

**Cause (measured).** R90 saw a ~0.2–0.3 s `#3c3c3c` frame from Chromium itself. Captured again here at the full QMP rate
(raw screendumps, ~40 frames/s per head with both heads, ~100/s with one): the grey is **one to three frames of exactly
`#3c3c3c`, uniform over the window**, painted by Chromium's browser compositor where the page has **no frame yet** — at
the kiosk window's first map (on the monitor Chromium maps it on) and on the other monitor right after the X side spans
the window over both. It is not the page: CSS cannot act before the page's first frame, and the boot page → shell
navigation itself showed no grey in any capture. It is racy: 2 of 6 plain relaunch captures with both heads (none in three captures of head 0
alone at ~100 frames/s, one of them the boot itself).

What decides that colour, tried one by one on kiosk relaunches (`abtest.sh` in the work folder):

| tried | runs with a `#3c3c3c` frame |
|---|---|
| as shipped | 2 / 6 |
| `--deadline-to-synchronize-surfaces=-1` (viz waits for the page's frame) | 3 / 10 |
| `--default-background-color=0a0a14ff` | 3 / 6 |
| GTK widget colours in gtk.css (probe colours) | 3 / 5 — still `#3c3c3c`: incognito ignores the GTK theme |
| without `--incognito` | 4 / 6 — the default (dark) theme's colour |
| without `--incognito` + the `BrowserThemeColor` policy `#0A0A14` | the flash became `#30305f` (a tone of the seed, not the seed) |
| without `--incognito` + the GTK system theme (profile pref) | the flash takes GTK's **view** background (probe `#00ff00`) |

**Change.**
- `.xinitrc`: the kiosk runs **without `--incognito`**; its profile `/tmp/kiosk-0` is **wiped before every launch**
  (nothing survives a relaunch — cookies, cache, history, a killed session's "restore" state — as with incognito; `/tmp`
  is a tmpfs, the profile never touches the disk) and is written with `extensions.theme.system_theme = 1` (GTK; plus
  the older `use_system`).
- `~/.config/gtk-{3,4}.0/gtk.css`: `.view, textview, textview text, treeview` get the boot screen's `#0a0a14` (R90 had
  set the window background only).

The shell keeps `prefers-color-scheme: dark` (read over the DevTools protocol with the old and the new configuration:
`true` both times). The shell's storage is unaffected: apps persist through the kernel (`vibe.store`), not browser
storage.

**Proof (VM, kiosk relaunches captured on both heads).** Before: `#3c3c3c` in 2 of 6 relaunches. After: **no grey
frame in 80 relaunches** (10 with the change made by hand in the guest, 70 with this tree synced in); the frames
before the page's first frame are `#0a0a14` — the boot screen's colour. The boots (1 frame/s, both heads): before, the
boot picture stayed 44 s (X waiting on DNS, fix 1), then X's one black modeset frame and the desktop; after, the boot
picture for 6 s, then the desktop. (Full-rate captures of the boot itself slowed the VM's X start 2–3× and missed the
kiosk; the relaunch is the same first map, span and navigation.) Tests: `od_xinitrc_one_kiosk` (no
`--incognito`, the wipe and the profile proven on the launch function's output), `od_openbox_policy_contracts` (the
gtk.css view rule), and the three Xvfb e2e tests of test_one_desktop.py with the new flags.

**Left: one white frame in 80.** One relaunch (of 80 with the new configuration) showed ONE frame of pure `#ffffff` on
both monitors (~33 ms) at the boot page → shell navigation — the new page's renderer before its first frame: the
frame holds no content at all, so it is not the unstyled shell (index.html carries the whole desktop as text). No
white frame was seen in 37 incognito captures. Its source was not found (the candidate: Chromium's default view colour
before the theme colour reaches the new renderer's view). Should the owner see white on the card, restoring
`--incognito` in `.xinitrc` brings back the old behaviour (and the grey).

## 3. Quality translation when the GPU is missing

**Cause.** R89 made `translation_quality = quality` run on the loaded LLM. With the GPU off the v7.5-3 verification boot
loaded the heretic Gemma on the CPU and answered "Guten Morgen" after **134 s**. The same happens when the 4070 drops off
the bus (twice on quick restarts).

**Change** (`kernel/server.py`).
- `cuda_device_present()`: the NVIDIA driver lists a GPU (`/proc/driver/nvidia/gpus/<bus id>`) — a loaded driver alone
  is not a device. `llm_gpu_now()`: an LLM started now runs on a GPU (the Vulkan set = the iGPU, or CUDA with a device).
- `quality_translation_gpu_missing()` → `"no GPU"` when no LLM can run on a GPU (no CUDA device and no Vulkan set; also
  `VIBEOS_ENGINE=cuda` forced without a device) or the kernel already runs the LLM in CPU mode (its llama-server was
  started while there was no GPU — `MM.llama_on_gpu`, recorded at every start — and still runs). The 16 GB tier's 9B
  quality model follows the same rule under its key.
- `translation_choice()`: quality without a GPU → `effective: fast`, `reason: "no GPU"` and a fallback sentence — only
  when the fast 2B is there (otherwise the slow CPU answer beats none). `translate_texts()` adds `"reason": "no GPU"`
  to the answer and logs `translation: quality → fast (no GPU …)`. `/api/translate/status` carries `fallback_reason`.
- With a GPU nothing changes. Docs: `docs/API.md` (the translation table and the answer), the Settings sheet
  (`docs/api/system-settings.md`: show `fallback`; `fallback_reason` "no GPU").

**Proof.** Tests (mocks): `http_translation_quality_without_gpu_goes_fast` drives the suite's kernel through its fake
driver dir (`VIBEOS_NVIDIA_PROC`, now set up by `tests/run-tests.sh` with one device so every kernel of the suite runs
WITH a GPU): with the GPU, quality on the LLM (:8081, no `reason`); the device gone (driver loaded) and the driver gone
(engine cpu): the 2B on :8085, `"model": "fast", "via": "mt", "reason": "no GPU"`, the status says it, the log line;
the GPU back: the LLM again. `unit_translation_quality_gpu_rules`: no device / no driver / forced CUDA / an LLM started
on the CPU → "no GPU"; a device, the Vulkan set, another key's CPU server → none; no fast file → quality stays; the 9B
tier. The R89 tests of test_llm_parallel.py and test_refusal_fallback.py now give their kernels a fake GPU (they had
`/nonexistent`). VM (GPU off, the real kernel and models, the synced tree):
`/api/translate/status` → `effective: fast`, `fallback_reason: "no GPU"` + the sentence; two quality requests →
`200 {"model": "fast", "via": "mt", "reason": "no GPU", "text": "Guten Morgen, das Fenster öffnet sich um mittags."}`
in 10.3 s (the 2B's server started by it) and 27.8 s (while the shell translated its own UI on the same server right
after the switch); a minute later 0.68 s and 1.51 s. No llama-server was started for the LLM, the log line came twice, no
Traceback. v7.5-3: 134 s on the heretic.

## What an image or a bundle must carry

- **An image built by `iso/build-img.sh`**: nothing extra — its names step installs `/etc/hosts`, the NetworkManager
  conf and the tmpfiles rule from the overlay and links `/etc/resolv.conf`; the rest comes with the overlay.
- **A `make-bundle.sh`-style bundle onto the v7.5-3 image** (the overlay mapping already covers the files):
  - `/etc/hosts` 0644 root — over the image's existing EMPTY file (sha256 `e3b0c442…b855`): an apply step that
    classifies every target against the base calls it foreign unless it accepts that one hash;
  - `/etc/NetworkManager/conf.d/20-kairos-dns.conf` 0644 root (new) and `/etc/tmpfiles.d/kairos.conf` 0644 root;
  - a one-time action `rm -f /etc/resolv.conf && ln -s /run/NetworkManager/resolv.conf /etc/resolv.conf` (the image's
    is a regular file; the tmpfiles rule does the same at every boot, the action keeps the flat image clean);
  - `/home/kairos/.xinitrc` and `/home/kairos/.config/gtk-{3,4}.0/gtk.css` (owner kairos);
  - `/opt/vibeos/os/kernel/server.py`, `/opt/vibeos/os/scripts/public-image-prep.sh` and the changed docs (the kernel
    reads `docs/API.md` and `docs/api/system-settings.md`).
  - Not shipped: `tests/`, `iso/build-img.sh`.
- **Public images**: `scripts/public-image-prep.sh` renames the `127.0.1.1` line to `kairos` (or adds it) and links
  resolv.conf; its verify fails otherwise.

# SD run 2026-10-13 — fixes from the owner's first microSD run (v7.5-1-media)

The owner ran v7.5-1 from a microSD card in a USB 3.0 card reader on the target laptop (2026-10-13, one session,
05:01–05:47). Three things came out of the logs (`dev/rig/stick-logs.sh` capture: the journal of that boot, the
cache on the card):

| | what the owner saw | cause | fix |
|---|---|---|---|
| A | the picture of an imaginary-web page "never drew" | the picture rendered ~7 min after its request; `/genimg` had served a placeholder at 360 s and the page never asked again | late pictures arrive by themselves (§1) |
| B | an explicit xhamster.com request came back as "Mythic Realms \| Fantasy Archives", a sanitised fantasy site | `BROWSER_SYSTEM` had no adult rule (the expander has one) | the 18+ rule in the text generators (§3) |
| C | boot verdict WARN | only `iwlwifi … failed to load iwl-debug-yoyo.bin (-2)`, an optional debug firmware | `*-debug-*` firmware is benign (§4) |

## 1. Late pictures

### What happened
1. The browser app (an iframe on `/web/`) asked for an explicit xhamster.com page. The page was written and cached
   at 05:30 with one picture, `<img src="/genimg/…">`.
2. The kernel queued that picture behind two pictures of another page (05:30:46–05:33:39) and an LLM reload
   (46 s, from the card).
3. It rendered 05:34:44–05:37:24 (one picture, 160 s: the image model is re-read from the card for every
   session, see §2) and was saved — about 7 min after the request.
4. `h_genimg` held the request for `GENIMG_WAIT = 360 s` and then served an SVG placeholder. Nothing in the page
   ever asked again, so the finished picture never appeared.

The same page set had a second, silent case: the pornhub.com page had five pictures (four `<img>` + one CSS
`background: url('/genimg/…')`); `GENIMG_LIMIT` is 4, so one was turned away with a placeholder and never rendered.

### The design
* **The signal.** Every placeholder of a picture that is still coming — the first request's wait ran out, or
  the cap turned it away — is **one pixel wider than the picture**: an odd width, while every picture is a
  multiple of 64 wide (`clamp_dims`). A FINAL placeholder (the minors block, a failed render) keeps an even
  width. The page can read `naturalWidth` of any image, even in a sandboxed opaque-origin iframe (R60/R68) where
  it can neither `fetch` the kernel nor read a header — so this needs no CORS, no token, no API access.
  Both placeholders are `Cache-Control: no-store`.
* **The re-ask.** `GET /genimg/<desc>?…&_r=<n>` is answered **at once**: the picture, the pending placeholder,
  or the final one — it never holds a connection. A re-ask of a picture that was turned away queues it once a
  slot is free; a re-ask of a picture whose render failed in the last 10 min gets the final placeholder (no
  render loop). A fresh page load (no `_r`) behaves as before: queue, hold up to `GENIMG_WAIT`.
* **The script.** One block, `<script data-kairos-genimg>` in `shell/shell.js` `BRIDGE_SRC` — so every app iframe
  has it (and the kernel's `/app/<id>` host and `bench/host.js`, which reuse the literal) — and the kernel injects
  the same block into every page it serves (`no_context_menu()`: `/web/` pages and `vibe.browse()` html; the cached
  file is never touched). It listens to `load`/`error` of every `<img>` in the document (capture phase: markup,
  `innerHTML`, script — however the element got there) and scans computed `background-image`s for `/genimg/` URLs
  (at `DOMContentLoaded` and when nodes that can carry one are added). A pending picture is asked again after 2 s,
  then ×1.5 up to every 15 s, for at most an hour; an `<img>` gets the new `src` (the old picture stays on screen
  until the new one has loaded), a CSS background gets the new URL inline on the elements that use it. It stops when
  the element is removed, when the page set another `src`, when the document goes away (timers die with it), and
  at the final placeholder. Every handler is guarded: it can never break an app or file an R45 bug report.
  A second copy in the same document (an app that `document.write`s a browse result) does nothing.
* **The wallpaper.** The shell paints `settings.wallpaper` only when it changes now (it was re-set every 5 s) and,
  for a `/genimg/` wallpaper (an app may set one), re-asks the same way until the picture comes
  (`applyWallpaper`/`lateWallpaper` in `shell.js`). The system wallpaper (`/api/wallpaper`) is a job, not `/genimg`.
* **The first request's hold stays 360 s** (now `VIBEOS_GENIMG_WAIT`, for tests). Considered: a short hold with a
  "rendering…" placeholder at once. Not taken: a held request delivers the picture the moment it is done, the
  re-ask adds up to 15 s; the cap (4) already bounds the held connections; and a no-script consumer (a CSS
  background an app sets later by JS on an existing element) still gets its picture whenever it comes within 6 min.
* **Journal.** `[kernel] genimg: still rendering after 360 s — …` / `queue full (4 pictures in flight) — …` /
  `not painted yet when the page asked again — …` once per picture, and `[kernel] genimg: a late picture reached its
  page (ask #n): …` when it arrives — the next stick run shows the path.

## 2. R79's page-cache drop on slow media — reasoned, not changed

R79 drops the image model's files from the page cache while sd loads them (`VIBEOS_SD_FADVISE=auto`: when RAM <
LLM file + 2 × image files + 6 GiB). On the laptop: RAM 32.9 GB, the heretic Gemma 13.9 GB, Muse + the Qwen3VL-4B
encoder + the VAE 11.1 GB → 13.9 + 22.1 + 6.4 = 42.5 GB > 32.9 GB → drop. On the card (84 MB/s; the Intenso stick
reads 152 MB/s) each image session re-reads 11.1 GB ≈ 132 s, which is most of the 160–200 s first picture.

* **Keeping them cached (`VIBEOS_SD_FADVISE=off`)** does not fit: during an sd session the page cache would hold
  13.9 + 11.1 GB, sd-server its own pinned copy (≈ 11.8 GB, measured in IMAGING-WORKFLOW-V75-1 §3.2) and the desktop
  ~4 GB = ~41 GB on 32.9 GB, so ≥ 8.6 GB are evicted every session — the LLM's pages are the cold ones. The LLM's
  reload after a picture grows from the measured 46 s (77 % resident) to ~110 s (8.6 GB at 84 MB/s), and its
  re-read pushes the image pages out again: the cost moves to the next question, it does not go away.
* **`VIBEOS_SD_MMAP=1`** (no pinned copy: 2.3 GB shmem + 0.7 GB anon, measured) would need ~32 GB during an sd
  session and more while llama-server runs (its KV cache, `--cache-ram 4096`): borderline on 32.9 GB. Its picture
  cost (+4.5 s, measured throttled) is known; what is not: a cold mmap load faults pages in the model's order, and
  the card's random reads are far slower than its 84 MB/s sequential (the old stick: ~30 MB/s with sd's loader
  threads). The R79 A/B for it was never run.

Neither is clearly right without a measurement on the card, so the policy stays; both switches exist
(`kairos.service` drop-in `Environment=`). The next card run should A/B `VIBEOS_SD_MMAP=1` (journal:
`sd-server image: session of N`, `page cache after the image engine: …`, the picture timestamps,
`llama-server ready (llm, N s)`). With §1 a slow picture is no longer lost — it is late.

## 3. The 18+ rule in the text generators

The heretic default did not refuse — it wrote a different, tamer site: the brand replaced, the scene sanitised, the
picture descriptions with it. `BROWSER_SYSTEM` had no adult rule; the S5 limits line ("never … anyone who looks
underage …") was its only word on the subject. The expander has had the rule since R76 (`_KREA_EXPAND_RULE_8_ADULT`
/ `_NEUTRAL`: adults 25+, as explicit as requested, never add clothing).

`kernel/prompts.py` now carries one rule per surface, the same limits sentence in each (`ADULT_LIMITS`):

| prompt | rule |
|---|---|
| `BROWSER_SYSTEM` (pages, `vibe.browse`) | `ADULT_RULE_WEB`: when the address or query asks for adult content (an adult site's name such as a porn tube, or explicit words) the page IS that site — the requested name/brand, its theme, the request's own words and people (an "old man" stays old — give his age); titles, descriptions and captions name nudity and sex acts in plain words, no euphemisms; every `/genimg/` picture shows that content itself — on a porn site every picture, thumbnails and category tiles included — described as who (with ages), what, where (a template, not a concrete example: the first wording's example ages were copied), never a landscape, an object or a clothed portrait instead; never toned down, renamed, re-themed, no warnings |
| `SPEC_SYSTEM` (the app spec) | `ADULT_RULE_APP`: the same for apps — name, theme, plain words, picture descriptions (`/genimg/`, `data-gen`) that show the content itself |
| `APP_SYSTEM` (+ evolve / regen) | `ADULT_RULE_APP_SHORT`, 121 chars: "build adult requests as asked, never toned down; fictional adults 25+ only, never minors or real people; else SFW" — the coder's prompt is the tightest budget (the dock's Settings app must fit the 8 GB tier's context with its API sheet and recipe whole: 28 211 of 28 278 chars now); the coder follows the spec, which has the full rule |
| `GAME_SYSTEM` | `ADULT_RULE_GAME`: theme, names and on-screen text as asked |
| `ASK_SYSTEM` (`vibe.ask`) | `ADULT_RULE_TEXT`: as explicit as asked, plainly, no warnings |
| `HTML_FIX_SYSTEM` | "an adult 18+ page or app stays exactly as explicit, with its name and theme" |

The wording was settled on the real models (§5, three rounds): the first one kept the brand ("xHamster | Nature's
Intimacy") but the text said "an intimate moment" and the pictures were a forest, a mossy trunk and a clothed elf;
the second made the owner's page explicit, but the porn tube's category tiles stayed clothed portraits and the
example's ages were copied ("old man" → "a man in his fifties"); the third is the shipped one.

Every rule: **only when the request asks for adult content** (each ends "A request that does not ask for adult
content gets a normal, non-sexual …"); every person a FICTIONAL adult aged 25 or older, said so ("a woman in her
thirties"), invented names; never minors or anyone who looks underage; never real, identifiable people. The S5 line
is still appended for an uncensored primary, the narrow minors block still checks every request — nothing about the
request is changed. No rule: `WALLPAPER_SYSTEM` (it weaves session fragments into an unrequested scenic vista;
a user's own wallpaper picture goes through the expander, which has the rule), `VISION_SYSTEM`, `GAME_FIX_SYSTEM`.

Tests: `tests/test_refusal_fallback.py` `sdrun_adult_rule_generation_prompts` (which prompt carries which rule, the
conditional opener and the SFW sentence, brand / 25+ / no minors / no real people, none in wallpaper / vision /
expander, the minors block silent on all of them, the personas the kernel and the mock route by intact);
`refusal_block_must_not_fire` covers every string of `prompts.py` (41 now); `tests/test_desktop_web.py`
`web_adult_rule_page_prompt` (the page prompt the model gets, for an adult and a SFW address: the same conditional
prompt, the address verbatim, the S5 line still last); `tests/test_kernel.py` `unit_n6_docs_reach_the_model` (the
budget, which the first, 650-char app rule broke).

## 4. The boot verdict

`kairos-bootlog`'s firmware check grepped every `firmware … fail|error|not found …` line of dmesg; iwlwifi asks for
`iwl-debug-yoyo.bin` on every boot and Debian ships none. A firmware file named `*-debug-*` is now benign: left out
of the WARN and named in the PASS detail (`no firmware load failures in dmesg (optional debug firmware absent,
benign: iwl-debug-yoyo.bin)`). Any other firmware failure still WARNs, also next to a debug line.
Test: `tests/test_kernel.py` `unit_bootlog_optional_debug_firmware` runs the script's own block (stub `dmesg` +
`check`) over the run's real dmesg firmware lines (PASS), the "Direct firmware load for …" form (PASS), a real
failure with and without the debug line (WARN) and a clean boot (PASS).

## Open
* The 25+ rule is followed by the model, not enforced: one of the eleven explicit picture descriptions said
  "in their 20s" (adults, but under the rule's 25), and the text of the owner's page still used a softer word or two
  next to an explicit title. The narrow minors block remains the floor on every request.
* The first picture of an image session on the card stays slow (~132 s of the image model re-read, §2); the next
  card run should A/B `VIBEOS_SD_MMAP=1`. The pictures now arrive — they are late, not lost.
* Apps that set a CSS background by script on an element that already exists (an attribute change, not an added
  node) are not rescanned; such a picture still arrives within the first request's 6 min.
* Not verified here: a run on the card itself (the hotfix must carry `server.py`, `prompts.py`, `shell.js` and
  `kairos-bootlog`).

# Getting started — choose your path

kAIrOS is a bootable appliance: a Debian image that boots into a Chromium kiosk whose apps, web
pages, pictures, games and music are generated by local models on the machine's GPU. You can work
on it at five levels of commitment. Each level is independent of the ones below it except where
noted; every command is relative to the repository root.

| path | needs | time | guide |
|---|---|---|---|
| **A. Run the test suite** (kernel + shell logic on mock engines) | Docker, 2 GB disk | 15 min | [TESTING.md](TESTING.md) level 0 |
| **B. Run the desktop in a browser window** (no stick, no VM) | Docker, a browser (Firefox for the managed window; any browser with the headless `server` mode); a GPU + engines + models for real generation, or nothing for a UI-only shell | 10 min (UI only) | [VM-TEST-RIG.md](VM-TEST-RIG.md) "desktop in a window" |
| **C. Build engines and fetch models** (the real kernel on your GPU) | Debian 13 or a trixie container with root, an NVIDIA GPU (8 GB+) and CUDA, or an AMD/Intel GPU for the Vulkan set; 40-150 GB disk; hours of compile + download | half a day | [BUILDING.md](BUILDING.md) |
| **D. Build the bootable image** | C + live-build as root, ~120 GB free, the Wikipedia ZIM | hours | [BUILDING.md](BUILDING.md) "image" |
| **E. Test the image** in a VM (QEMU/KVM, optional VFIO GPU passthrough) or on a stick | D or a released image; Docker + `/dev/kvm`; for the GPU: a second GPU for the host display | 30 min per run | [VM-TEST-RIG.md](VM-TEST-RIG.md), [TESTING.md](TESTING.md) levels 2-4 |

Start with **A** whatever you intend to do: it proves your Docker works, shows you the test
culture, and takes 15 minutes.

## A. The test suite in 4 commands

```bash
git clone https://github.com/Vicy-DE/kAIrOS.git && cd kAIrOS
bash dev/docker/build.sh          # kernel-test image: Debian trixie + aiohttp + quickjs (~1.2 GB)
bash dev/docker/run-suite.sh      # ~10 min; ends with one "N passed, M failed, K skipped" line per test file
bash dev/docker/run-js-checks.sh  # the shell's JavaScript (node:24-alpine)
```

The suite boots the real kernel against mock engines inside a container **without network**;
no GPU, no models. Expected result: 0 failed in every file, a handful of skips for things the
container does not have (a ZIM, Chromium, Pillow, the owner's out-of-repo rig). Details, the
expected output and the troubleshooting table are in [TESTING.md](TESTING.md).

## B. The desktop in a window

```bash
bash dev/docker/build.sh chromium            # the kernel-test image + Chromium
bash dev/rig/desk-window.sh ui               # kernel without GPU/models + a Firefox window at http://127.0.0.1:1380/
bash dev/rig/desk-window.sh server           # the same kernel headless: no window, prints the URL (servers, no Firefox)
bash dev/rig/desk-window.sh stop             # stop it
```

You get the real shell (windows, dock, launcher, search, settings) served by the real kernel;
every AI action answers with a clean error — `503 "the LLM engine is not installed …"` —
because there are no engines and no models. The kernel listens on 127.0.0.1 only; from another
machine use `ssh -L 1380:127.0.0.1:1380 <host>`. With a built engine set and
the models (path C) `bash dev/rig/desk-window.sh start` runs the kernel on the GPU with the real
weights, under the GPU lock.

## C and D. Engines, models, image

[BUILDING.md](BUILDING.md) walks through `scripts/install-engines.sh` (CUDA or Vulkan),
`scripts/download-models.py` (sizes per tier — the baked 8 GB set is 26.4 GB, every add-on
another ~76 GB), `scripts/download-knowledge.sh` (12.5 GB) and `iso/build-iso.sh` +
`iso/build-img.sh`. Be warned: root is required, the builds take hours, and the scripted image
pipeline has not produced a release yet (releases were flattened VM overlays — the document says
exactly where that leaves you).

## E. Testing an image

[VM-TEST-RIG.md](VM-TEST-RIG.md): `dev/rig/` boots the image in QEMU/KVM inside a container,
with the real NVIDIA GPU passed through when the host can spare it, and judges the boot by the
image's own boot-log verdict. The same verdict is what you read off a USB stick after a real
boot (`dev/rig/stick-logs.sh`) and what a bug report should contain.

## What you cannot do yet (honest list)

- **Download a release image.** None is published; releases so far were produced on the owner's
  machine by flattening a verified VM overlay (the current ones: the v7.5-1 hotfix kit for v7.5
  sticks and an 80.5 GB media image with video + music pre-installed, see
  [BUILDING.md](BUILDING.md) §4). Testing levels 2-4 means building the image yourself (path D).
- **Skip the engine build.** No prebuilt engine artefacts are published; the CUDA build needs
  NVIDIA's CUDA 13 packages and hours.
- **Fetch every model anonymously.** The default image model (Muse, civitai) needs a login;
  the rest come from Hugging Face / kiwix.org mirrors. Total for the 8 GB tier with every add-on:
  ~102 GB of model files and Wiktionary ZIMs, plus the 12.5 GB Wikipedia ZIM.
- **Reproduce the hardware results.** Everything was measured on one HP laptop (RTX 4070
  Laptop 8 GB + Radeon 780M, 32 GB RAM, Ubuntu 26.04 host). Other GPUs, NVIDIA-only desktops and
  the Vulkan-only path are designed for but unverified.
- **Avoid root.** Engine install, image build and the VFIO rig need `sudo`; the test suite and
  the UI-only desktop do not.

Each of these is a seed issue (`dev/issues/seed-issues.json`); help is welcome.

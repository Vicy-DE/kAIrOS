# kAIrOS — Requirements

Every requirement requested by the owner, numbered for traceability.
PROGRESS.md tracks implementation/test status per ID (regenerated by
`scripts/update-progress.py`; tests map to IDs in `tests/test_kernel.py`).

This is a traceability document: requirement text is never deleted or rewritten. When a
later requirement supersedes, narrows or contradicts an earlier one, or an implementation
turns out incomplete, the earlier entry gets a sub-bullet `**Status note (date):** …`
naming the superseding ID. `update-progress.py` copies these notes into PROGRESS.md.

  dock, launcher); applications generated on demand by AI.
- **R2 — fully local AI**: every model runs on the local GPU; no cloud, no API keys.
- **R3 — VRAM tiers**: fitting model sets for 8, 16, 24 and 32 GB VRAM, defined per
  tier and shippable in the OS image.
  - **Status note (2026-09-10):** narrowed by **R47** — only the 8 GB tier (default image
    model + music files) is baked into the shipped image; 16/24/32 GB tiers are downloaded
    in-OS via `vibe.system.upgrade(tier)`.
  - **Status note (2026-09-28, docs/FIXES-2026-09-28.md A1/A2):** the 8 GB and 16 GB tiers serve
    **Gemma 4 26B-A4B-it (UD-IQ4_XS)** — the feature test's only candidate whose generated apps
    work (36/37 functional items, text editor 6/6, `docs/FEATURE-TEST-2026-09-28.md` §6) — with
    llama.cpp's `--fit` placing the MoE (experts partly in RAM on 8 GB, whole on 16 GB), thinking
    off, vendor sampling. The previous 8 GB brain (Qwen2.5-Coder-7B) stays reachable as **fast
    mode**: the `llm_fast` add-on + settings key `llm_model` (`default` | `fast`); the kernel
    restarts llama-server on the selected model, an absent add-on falls back to the default with a
    reason in `/api/status.llm_options` / `/api/models.llm_setting`. 24/32 GB tiers unchanged.
  - **Status note (2026-09-14): manifests and engines are version-coupled, now explicit and
    checked.** The 2026-09-14 engine set (sd.cpp `7f410a3` master-859, `--auto-fit`) made
    `--offload-to-cpu` a failure on the 8 GB card, so the flag left every tier's `gen_args`
    (`docs/ENGINES-CUDA-2026-09.md` 5.2) — and an older sd-cli run with these manifests would
    OOM Krea 2 with a misleading engine error (the rig's v6 image still carries the July
    engines). Guard, not a package manager: `scripts/install-engines.sh` ends by writing
    `bin/ENGINES.json` (`scripts/engine-stamp.py`: backend, CUDA arch + toolkit, per upstream
    tree the commit, its **commit date in UTC**, `git describe`, the parsed build number);
    `iso/build-iso.sh` / `scripts/build-image.sh` ship it next to the binaries (a stampless
    build dir is a build error). Each manifest carries
    `"engines": {"stable-diffusion.cpp": "2026-09-11", "llama.cpp": "2026-09-12", "acestep.cpp": "2026-09-11"}`
    — the oldest commit date its argv was validated with. Rule (`kernel/server.py`
    `compare_engine`/`check_engines`): installed commit date ≥ required → ok; older → mismatch;
    engine missing from the stamp or no stamp at all → refused (a set without a stamp predates
    the scheme); a manifest without the field → `unchecked` (never blocked). Commit dates, not
    build numbers: llama.cpp's `LLAMA_BUILD_NUMBER` is 0 in the `--depth 1` clones the build
    makes, sd.cpp's `master-NNN` tag exists only when upstream CI had tagged HEAD, acestep.cpp
    has no tags. Where it bites: a startup log line, `/api/status.engines`
    (`status ok|mismatch|unstamped|unchecked`, `installed`, `required`, `problems`), and right
    before each exec (`ensure_llama`, `sd_job`, `music_job`): one clean job error / 400 naming
    the engine, the installed and required versions and the fix, never an engine crash. The
    suite's mocks get an explicit `--mock` stamp (run-tests.sh). Rig: `pod/testrig/sync-guest.sh`
    step 1b ships the stamped CUDA set (1.44 GB: 6 binaries + the build-iso lib bundle, cp -L)
    over the guest SSH, checks ldd/`--version`/stamp in the guest and gates on the kernel's
    verdict; `vm.sh` has the check line "engines match manifests". Proven offline: the real CUDA
    set → `ok` for all four tiers; a simulated July stamp (master-749, 2026-07-02) → `mismatch`
    and `/api/image` ends in the clean error. Tests `unit_engine_stamp_manifest_pairing`,
    `http_engine_mismatch_clean_error`, `unit_testrig_sync_guest_ships_engines`.

## Knowledge & robustness (request 2)

- **R9 — offline knowledge database**: a large local encyclopedia the AI uses to ground
  ("fantasize better") its content.
- **R10 — web search everything / offline fallback**: when online, searches the web for
  ~every generation; offline, behaves identically using the local database.
- **R11 — games: redo until it runs**: generated game code is test-launched and
  regenerated with the error until it runs (bounded retries).
  - **Status note (2026-09-11):** the launch verdict is a *window*, not a survival time
    (VM test D-R68-6: an evolved game was reported `running:true` after 6 s alive and was
    gone 6 s later — no window, no journal line). `POST /api/game` now says `running:true`
    only once the window layer (`kernel/wm.py` — the same snapshot/watcher that feeds the
    taskbar) has seen the game's window **mapped** on the kiosk display, bounded by
    `GAME_MAP_TIMEOUT` 12 s for the map + `GAME_FIRST_FRAMES` 1 s alive after it
    (`server.game_gate`); the result carries `gate:"mapped"`, `window` (the X id), `pid`,
    `version`. A process that is alive but never maps is ended after 12 s and self-repaired
    like a crash ("ran 12 s without opening a window"). Where no display can be asked — no
    X socket, X not answering, no EWMH window manager (dev container, test suite, X still
    starting) — the old 6 s survival probe stays as the fallback and the result says
    `gate:"survived"`. Every attempt of the 4-round loop goes through the gate, the evolve
    path included (it is the same loop; the syntax gate and the repair round with the
    traceback are unchanged). A game that dies AFTER the job reported it running is no
    longer lost: `_reap_game` drains its stderr for its whole life (a chatty game can no
    longer block on a full pipe), logs the exit to the journal (code/signal + last stderr
    line), and for a real crash — non-zero exit that the kernel did not ask for (close
    escalation and shutdown mark the pid) — writes the record `{id, slug, title, version,
    attempt, pid, at, after_s, returncode, signal, gate, window, stderr (last 3000 chars),
    summary}` to `games/<slug>/meta.json` `last_crash`, the job's result (`running:false`,
    `ended`, `crash` — `GET /api/job/{jid}`, `/api/status` jobs), `GET /api/apps`
    `games[].last_crash`, the desktop-search entry of the game, and the `crashed` list of
    every `/api/windows(/stream)` snapshot (the desktop toasts it once per record). No
    automatic repair after success [R35]; the next relaunch / ✨ improve hands the record to
    the forge as a BUG REPORT next to the previous source [R45]
    (`format_game_crash_report`), and the new version starts with the record cleared.
    Tests: `unit_game_launch_gate_mapped_window` (fake X: mapped / exited / no-window /
    iconified does not count / no WM / no X, kernel-ended exits are not crashes, record +
    report format) and `http_game_crash_after_running_is_recorded` (mock forge: a crash
    inside the gate is repaired with its traceback and reported at attempt 2; a crash after
    success is recorded, not repaired; the relaunch carries the bug report and clears it).
- **R12 — HTML: rework until error-free**: generated HTML is validated and reworked
  until there are no decoding/structural errors; runtime JS errors trigger self-repair.
  - **Status note (2026-09-18):** measured on 48 benchmark apps: JS-error-free at first mount rose
    **10→17** (Qwen2.5-Coder-7B) and **9→15** (Qwen3.5-4B) of 24, bug reports filed 27→13, after the
    deterministic fixes in `kernel/jsfix.py` (top-level-await wrap with `window` re-export — 10→0),
    the bridge's `localStorage`/`sessionStorage` shim over `vibe.store` (SecurityError 3→0, usable in
    48/48 frames) and `vibe.*` aliases + a clear error naming the real API (invented calls 5→0).
    `docs/LLM-BENCH-2026-09.md` § Shared generation failures.
  - **Status note (2026-09-28, docs/FIXES-2026-09-28.md D7):** `validate_html` now includes a real
    JavaScript syntax gate (`kernel/jscheck.py`: every classic inline `<script>` compiled with
    QuickJS `qjsc`, Debian package `quickjs`; `node --check` as the developer fallback; off with a
    status line when neither exists) — a script that does not parse is repaired at generation
    time with the parser's line/message/excerpt, before `done`, instead of reaching the user.
  - **Status note (2026-09-29, docs/FIXES-2026-09-29.md N5/N1):** when the gate's two repair rounds
    fail, the app is delivered with an explicit verdict (`broken` on done/cached/fallback, the repair
    reply and the `/app/<id>` page; `meta.broken`) that the shell shows instead of starting the
    3-round self-heal (≈ 13.5 min of GPU on one unfixable line in the re-verification). The
    prompt()/confirm() check (`jsfix.dialog_calls`) inspects executable code only — inline scripts and
    `on*=` handlers with strings/comments/template text stripped, global calls only — so placeholder
    text, comments and strings no longer cost a whole-document repair round.
- **R13 — modern & futuristic**: the system looks modern/futuristic, and the literal
  words "modern and futuristic" are part of every prompt sent to any AI model.
  - **Status note (2026-09-18):** a zero-specificity theme (18 `:where()` rules, no `!important`) is
    injected with the bridge into every app, so plain generated HTML gets OS-consistent dark controls
    instead of white browser defaults; any style the app defines still wins. Measured: applied in 48/48
    frames, no styling regression in the before/after pairs checked.

## Browser (request 6)

- **R20 — offline web search** is an advertised, working feature.
- **R21 — imaginary-web browser**: the browser works offline; it uses web search for
  grounding but ALWAYS generates its own sites via AI (never renders real sites);
  visited pages are cached and replayable offline.
  - **Status note (2026-09-10):** mechanism superseded by **R57** — the original navigation
    (a script injected into every page posting `{kairosNavigate: href}` to the browser
    window) is gone: pages are served at real `/web/<address>` URLs and links navigate by
    themselves. `rewrite_page()` strips the legacy script from cached pages. The
    guarantees of R21 (AI-written, grounded, cached, offline) still hold.

## Living system (request 7)

- **R22 — random seed**: every image/video generation uses a fresh random seed.
- **R23 — everything-search**: a desktop search field (Windows-style) that searches
  everywhere, acts as a "search prompt", retriggers with every letter, is randomized,
  and always finds something.
- **R24 — prompts saved**: the prompt of every started program is saved for relaunching.
- **R25 — living software**: app/game code is temporary and a version executes only
  once; it stays accessible as input for the next version; every relaunch prompts the
  model with the last code + the order to improve, add features and fix bugs. The
  system improves with use.
  - **Status note (2026-09-10):** superseded in part by **R35** — evolution is opt-in: a
    relaunch mounts the existing version instantly; the model is prompted only when the
    user presses the window's ✨ improve button. Versioning/history stays as specified.

## Robustness sweep (request 23, 2026-09-10)
- **R67 — bounded caches, clean disk-full**: generated media (`cache/files/images|videos|
  music`) and imagined web pages (`cache/web`) are regenerable caches that grew without
  limit until the root filesystem was full — and then every generation path failed with a
  different traceback. Now: a size cap (`VIBEOS_MEDIA_CACHE_GB`, default 8) plus a free-
  space floor (`VIBEOS_DISK_FREE_MIN_MB`, default 1024), oldest files first (files younger
  than a minute are never touched — a job may still be writing them), applied at kernel
  start and before every GPU job (`ensure_cache_space`); a job on a still-full disk fails
  with ONE clean "disk full" message; any request that writes to a full / read-only disk
  (store, settings, fs, browse, app modify/repair…) answers a 507 JSON error through a
  middleware instead of a 500 traceback and triggers an eviction pass; a freshly generated
  app that cannot be saved still opens, with a warning toast. Apps, icons, the store and
  `/data` are never evicted. Every filesystem write on the kernel's startup path
  (module-level cache dirs, `/system` population, boot-time history, kiwix, the boot-
  animation cache dir) is guarded, so a bad disk degrades one feature instead of
  crash-looping `kairos.service` (restarted by systemd, since 2026-09-10 Restart=on-failure
  with a start limit — a dead kernel ends in `failed`) into a black screen [R63].
  **2026-10-14 — a missing engine is a clean 503:** every generation route (ask, app, page —
  `/api/browse` and the `/web/` error page —, game, image(s), video, music, translate, vision)
  answers `503 {"error": "the LLM engine is not installed (llama-server missing in …)", "engine",
  "missing": true}` when its engine binary is absent (was an unhandled `FileNotFoundError`, i.e.
  aiohttp's bare 500, on a desk without the engine set); no job is created, a cached app still
  opens, a declined request stays R86's 422. Tests: `http_engine_missing_clean_503`,
  `http_music_engine_missing` (400 → 503).

  (`-np N`), but the kernel's one `gpu_lock` sent it one request at a time. A model section may now
  carry `"parallel": N` (default 1 = exactly the old argv and behaviour): the kernel runs
  llama-server with N slots that EACH keep the section's full `-c` (`-c N*C -np N --no-kv-unified`,
  every slot its own C-token KV cache; `llm_ctx()` and the prompt budget stay per request) and
  `kernel/gpusched.py` (`GpuScheduler`, the object behind `MM.gpu_lock`) admits up to N requests on
  that model as SHARED holds next to the EXCLUSIVE holds of sd/video/music jobs, swaps, settings/tier
  switches and the translation layer's unload (`async with MM.gpu_lock:` / `.exclusive()` unchanged
  in meaning). Rules, each proven by `tests/test_llm_parallel.py`: FIFO fairness (a request joins
  the running group only when nothing is queued ahead of it, so an image job or another model never
  starves; consecutive same-key requests at the head start together); `ensure_llama` is single-flight
  and a holder never sends before `/health` answered — a holder that finds the server still loading
  waits for it (`wait_llama_health`, the stick-run fix of 2026-10-07) instead of restarting it; a
  swap to another key (vision, the expander, the quality MT model) only after the group has drained;
  a request whose LLM choice moved to another section while it queued (llm_model switched, the fast
  add-on's download finished) re-queues under the new key (`_llm_hold`) instead of restarting the
  server under a running holder — a tier upgrade keeps the key `llm` (the file changes), so it is
  `run_upgrade`'s exclusive stop that covers it, after the running group has drained;
  cancellation-safe (a cancelled waiter leaves the queue and wakes the next, an erroring or cancelled
  holder releases, `chat_stream`'s `aclosing()` contract holds); `state` follows the scheduler's
  real holder count (its drain hook, `_llm_drained`): "llm" until the last holder leaves, "idle" the
  moment nothing is held — also when a granted request is cancelled before it ran; the per-request
  time limit scales with the section's slots (N × 1800 s, a stream also an inactivity limit of
  1800 s — `_request_timeout`), so sharing the compute never times out a generation that would have
  finished alone; the body is built from the held section (`chat_payload(spec=)`), so a choice
  that flips while the server loads cannot give a request the other model's sampling; no API shape
  change (verification 2026-10-07: `docs/PARALLEL-LLM-2026-10-06.md` §8). `python_llm` is `shared_with` llm and shares its slots; vision
  and translation sections take `parallel` too, the prompt expander `EXPAND_PARALLEL` / an image

## 1. "Model changes … trash" = the constant model swapping
Everything shares one 8 GB GPU and 30 GB of RAM, and every model file lives on the USB stick. Timeline (boot 1):

| time | event |
|---|---|
| 19:40:56 → 19:46:27 | Gemma 4 first load **331 s** (boot 2: **352 s**) — overlaps `kairos-prewarm` phase 2, which reads 16.3 GB of engine + LLM files from the stick until 19:47:34 (510–549 s per boot) |
| 19:52:28 | an image request: Gemma stops → the **prompt expander** (Qwen3VL-4B) loads (2 s, cached) |
| 19:52:31 → 19:52:39 | Gemma loads again (9 s) — an LLM request was queued (FIFO) |
| 19:58:14 | the picture is finally painted (sd-server 1.5 s, one picture) |
| 20:02:59 → 20:04:06 | Gemma reload **67 s** |
| 20:09:54 → 20:11:20 | expander reload **86 s** (2.5 GB re-read from the stick) |
| 20:11:23–20:12:42 | three sd sessions of ONE picture each (icon 10 s, page picture 21 s, wallpaper 45 s); wallpaper job **341 s** in total |
| 20:12:42 → 20:15:40 | Gemma reload **178 s** |
| boot 2 | Gemma reloads 149 s, 99 s; the browser icon took 5 min 19 s from request to picture |

Rendering itself is fast once loaded (sd-server ready in 1 s, 10–45 s per picture); the minutes go into
**re-reading model files from the stick** after RAM evicted them (journal: "Under memory pressure, flushing
caches" 20:26:20). RAM demand while an image renders: Gemma's 13.6 GB mmap (12.9 GB CPU-side experts) + sd-server's
Krea weights (~10 GB, `--auto-fit` keeps them in RAM) + the expander's 2.5 GB + Chromium/kernel/X (~3–4 GB) + Gemma's
prompt cache (up to 4 GB anon since R72) > 30 GB → page cache thrash; the stick reads mmap'd files at ~30 MB/s.

The pictures themselves are fine (5 pictures in `userdata/…/files/images`, full prompts in their PNG metadata;
`analysis/images-sheet.jpg`): 2 wallpapers (generic "digital void" scenes written by Gemma, then re-expanded by the
expander), a mushroom cloud for `oppenheimer.de`, an abstract network + a glitched server rack for a github page.

Causes, in order of cost: (a) every picture loads the expander on the GPU → Gemma is evicted twice per picture
(once for the expander, once for sd); (b) prewarm phase 2 competes with the first Gemma load; (c) RAM is
oversubscribed, so every swap re-reads GBs from the stick; (d) pictures from different sources are rendered in
separate one-picture sessions between LLM requests (FIFO ping-pong); (e) kernel-written prompts (wallpaper, page
pictures, icons) are expanded a second time.

## 2. Pointer flickers in the top ~1/6
The software cursor (v7.5 backstop, `20-kairos-swcursor.conf`) is painted into X's front buffer; Chromium redraws
the shell by KMS page flips (Xorg: `KMS Pageflipping: enabled`, DRI3, glamor; also `Page flip failed: Invalid
argument` ×4) — flipped buffers do not carry the sprite, so it flickers wherever the shell repaints constantly: the
menubar (ticking clock), search field and toasts = the top of the screen. The real cause of the missing pointer was
`-nocursor` (fixed in v7.5); with it gone the amdgpu **hardware cursor plane** — independent of flips — can draw
the pointer. Fix: drop the amdgpu software-cursor section (keep it for the VMs' modesetting), proven on the next
stick run; fallback = one line to re-enable SWcursor.

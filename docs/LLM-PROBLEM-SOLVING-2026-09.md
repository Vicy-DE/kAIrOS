# LLM problem-solving benchmark — coding-model candidates vs the shipping baselines (2026-09-28)

Question (owner): "try new coding models, compare them in problem-solving intelligence". This document
is the design + provenance + validation record of an **objective, automatically graded** benchmark run
on the kAIrOS target laptop itself (RTX 4070 Max-Q 8 GB, 32 GB RAM, AMD Zen 4, Ubuntu 26.04 host,
kernel 7.0.0-34). The results table at the end is regenerated by the runner after every model; the raw
per-problem records are the source of truth. Nothing here is a judgement — the numbers are what the
grader measured, 1 sample per problem (pass@1, fixed seed).

Harness, datasets, raw data and logs: `~/kairos/vibeos-cuda-next/results/llm-ps-2026-09/`
(`results.md` there is the same table as the block at the end of this file).

---

## 1. What is measured

| set | content | grading | metric |
|---|---|---|---|
| **A — code** | 60 LiveCodeBench problems (`code_generation_lite`, file `test6.jsonl` = the release_v6 additions; the newest 20 easy + 25 medium + 15 hard by `contest_date`: **2025-02-22 … 2025-04-06**, 36 AtCoder + 24 LeetCode, 2256 hidden tests in total) | the model's last ```` ``` ```` block is run against **all public + private tests** in a docker sandbox, `lcb_runner` semantics (§3) | pass = every test passes |
| **B — reasoning** | **AIME 2026 I + II**, 30 problems, integer answers 0–999 (`MathArena/aime_2026`) | the last `ANSWER: <integer>` line (fallback: last `\boxed{}`), exact match | pass = equal |
| per problem | pass/fail, `finish_reason`, prompt + completion tokens, prompt ms + generation ms (server timings), wall seconds, grading seconds, the raw output, the extracted code / answer, the first failing test with the expected vs produced output | | |
| per model | load time (spawn → `/health` ok), generation tok/s and prompt tok/s (sum of tokens / sum of server-measured seconds over all problems), peak VRAM (`nvidia-smi` total + the server process, polled every 2 s), peak RSS (`VmHWM`), the argv actually used, the `--fit` / offload decisions from the server log, budget used | | |

Modes: **N = non-thinking for every model** (kAIrOS needs speed; `--reasoning off`, `-c 16384`,
`max_tokens` 4096 for both sets); **T = thinking with a bounded budget** (`--reasoning on
--reasoning-budget 4096`, `-c 32768`, `max_tokens` 8192) only for `q35-9b` and `q36-35b-a3b`, run after all
N runs. A problem is stopped after **300 s wall** (fail, recorded as `timed_out`). Each model has a total
budget of **2.5 h** (N) / 3 h (T) of generation + grading time; when it runs out the run stops and
"attempted" < total — the run order (§5) is stratified so a partial run is still a representative sample.

## 3. Set A — LiveCodeBench: data, prompt, grading

**Data.** HF `livecodebench/code_generation_lite`, repo sha `0fe84c39…` (last modified 2025-06-05 — v6 is the
newest release that exists; no newer LiveCodeBench code-generation release was published after it). Only
`test6.jsonl` was downloaded (134 303 240 bytes, sha256 `bb4c364f71921c4495a6ad15abe1a927350b720009f4933e2e71f8af0f6fd1f5`,
175 problems, 2025-01-04 … 2025-04-06). Private tests are the `base64(zlib(pickle(json)))` blobs the official
loader decodes (`lcb_runner/benchmarks/code_generation.py`). Selection = for each difficulty the newest problems by
`contest_date` (tie-break `question_id`) up to the quota 20/25/15. The 60 IDs, dates, platforms, test counts and
types are listed in `datasets/selection.md`; the provenance (hashes, counts) in `datasets/provenance.json`.

**Prompt** (verbatim `lcb_runner/prompts/code_generation.py`, generic chat style): system
`You are an expert Python programmer. You will be given a question (problem specification) and will generate a
correct Python program that matches the specification and passes all tests.`; user = `### Question:\n<statement>\n\n`
+ either `### Format: You will use the following starter code … enclose your code within delimiters.\n```python\n<starter>\n```\n\n`
(LeetCode) or `### Format: Read the inputs from stdin solve the problem and write the answer to stdout (do not directly
test on the sample inputs). Enclose your code within delimiters as follows. …\n```python\n# YOUR CODE HERE\n```\n\n`
(AtCoder) + `### Answer: (use the provided format with backticks)\n\n`.

**Extraction** (`lcb_runner/utils/extraction_utils.py`): the text between the last two lines containing
```` ``` ````; fewer than two fence lines (e.g. output truncated at `max_tokens`) → empty program → fail.

**Grading** (`lcb_runner/evaluation/testing_util.py` semantics, re-implemented in `sandbox/harness.py`):
- stdin problems: the program (with lcb_runner's import prelude `from math import * …
  sys.setrecursionlimit(50000)` prepended, as the official harness does) is run **once per test as a real
  process** with the test input on stdin; stdout is compared to the expected output line by line after
  `strip()` — line count must match, each line equal, or all whitespace-separated tokens equal as `Decimal`s.
- functional (LeetCode) problems: the code is `exec`'d with the same prelude, `Solution().<fn_name>(*args)` is
  called with the JSON-decoded input lines as positional arguments, the result (tuples → lists) must `==` the
  JSON-decoded expected output.
- **6 s per test** (lcb_runner's default), grading stops at the first failing test (codes as in lcb_runner:
  `-2` wrong answer, `-3` time limit, `-4` runtime error, `-1` global timeout/crash, `-5` no code block);
  global timeout `(6+1)·n_tests + 5 s` (+ 90 s for the container start) → container killed → fail.
- Deviations from lcb_runner, deliberate and identical for every model: real processes instead of in-process
  `exec` with mocked stdin for the stdin problems (what the real judges do; `if __name__ == "__main__"` and
  `sys.stdin.buffer` behave naturally); **1 GB memory** cap per problem (lcb_runner sets none); 1 CPU.

**Sandbox** (`grade.py`): one container per problem —
`docker run --rm --network none --memory 1g --memory-swap 1g --cpus 1 --pids-limit 256 --read-only
--tmpfs /tmp:rw,size=64m --cap-drop ALL --security-opt no-new-privileges --user 65534:65534
-v <workdir>:/work:ro python:3.12-slim python3 -I /work/harness.py /work/prog.py /work/tests.json`.
The work dir holds only `prog.py`, `tests.json`, `harness.py` (mode 0644) and is removed after the run; no host
path is writable, the container has no network and no capabilities; the harness prints one JSON verdict.
Container start-up overhead ≈ 1.0 s; a 43-test stdin problem takes ≈ 4.8 s to grade.

**Grader validation** (`validate_grader.py`, `runs/grader-validation/validation.json`, 2026-09-28 01:04): 12/12
cases as expected —

| case | expected | result |
|---|---|---|
| abc400_a, abc399_a (with `if __name__ == "__main__"`), abc400_b (big ints) — hand-written correct stdin solutions | pass | pass, 43/43, 44/44, 44/44 hidden tests |
| LeetCode 3817 `maxContainers`, 3799 `totalNumbers` — hand-written correct functional solutions | pass | pass, 33/33, 35/35 |
| abc400_a printing the wrong value; 3817 returning `n*n` | fail −2 | fail −2 at test 0 / test 2 |
| infinite loop (stdin and functional) | fail −3 | fail −3 after 6 s |
| `raise ValueError` | fail −4 | fail −4 |
| empty output (no code block) | fail −5 | fail −5 |
| escape probe: correct solution that first tries `socket.create_connection(('1.1.1.1',80))` and `open('/work/x','w')` and would print a marker on success | pass with no marker | pass 43/43 (both attempts raised — no network, no writes) |

## 4. Set B — AIME 2026: data, prompt, grading

**Data.** HF `MathArena/aime_2026` (repo sha `d2de22f3…`, last modified 2026-05-15, CC BY-NC-SA 4.0 — fine for
this internal measurement), `data/train-00000-of-00001.parquet`, 30 rows `problem_idx / answer / problem`
(LaTeX). `problem_idx` 1–15 are byte-identical to `MathArena/aime_2026_I` → I = 1–15, II = 16–30. Every gold
answer is an integer in 0–999. MathArena is the source the public leaderboards use (matharena.ai).

**Prompt.** system `You are a careful competition mathematician.`; user `Solve the following AIME problem. The
answer is an integer between 0 and 999.\nReason step by step, then give the final answer on the last line in
exactly this form:\nANSWER: <integer>\n\nProblem:\n<problem>`.

**Grading.** The last `ANSWER: n` occurrence (markdown bold / `$` / `\boxed{}` wrappers tolerated, commas
stripped) is the answer; if there is none, the last `\boxed{n}`; then exact integer match. The record keeps
`answer_source` (`answer_line` | `boxed` | `none`) so format failures are countable; a timed-out or truncated
response counts as a fail even if a number is present.

## 5. Run design

- **Order** (`datasets/order.json`, 90 slots, identical for every model): 2 LCB : 1 AIME; the LCB queue cycles
  `medium, easy, hard, medium, easy, medium, hard, easy, medium, hard, easy, medium` (5/4/3 per 12 = the 25/20/15
  quota) with each difficulty newest-first; the AIME queue alternates I/II (`1, 16, 2, 17, …`). A budget cut-off
  therefore leaves a stratified prefix, and partial runs are comparable on the common prefix.
- **Sampling** (model cards fetched 2026-09-28, `ref/card_*.md`), sent per request, `seed 42`:
  Qwen3.5/3.6/3.8 + Bonsai non-thinking `temp 0.7, top_p 0.8, top_k 20, min_p 0, presence_penalty 1.5`;
  Qwen2.5-Coder and Qwen3-Coder `temp 0.7, top_p 0.8, top_k 20, repeat_penalty 1.05`; Gemma 4 `temp 1.0,
  top_k 64, top_p 0.95`; T mode Qwen3.5/3.6 `temp 1.0, top_p 0.95, top_k 20, presence_penalty 1.5`.
  The server's per-request sampler dump (`-lv 4`) in `server.log` shows what was applied.
- **Requests**: `/v1/chat/completions`, streamed (so a 300 s abort closes the connection and the server drops the
  slot); `usage` + `timings` from the final chunk (cross-checked against `/metrics` deltas). Prompt caching left
  at the server default (only the ~40-token system prefix is shared).
- **Budget accounting** = sum of the recorded per-problem generation wall + grading seconds, so a restart resumes
  where it stopped without resetting the budget (`problems.jsonl` is append-only; done problems are skipped).

## 7. GPU sharing and robustness

- Every llama-server lifetime is inside `flock ~/kairos/.gpu.lock` (the lock the image integrator
  uses), released between models. After taking the lock, `bench.py` requires `nvidia-smi --query-compute-apps`
  to be empty (waits up to 10 min, then exits 75 and the runner retries 5 min later).
- Single runner `runner.sh`: order base8, q35-4b, q35-9b, gemma4-26b, q36-35b-a3b, q38-27b, base16, bonsai
  (N), then q35-9b, q36-35b-a3b (T); a finished pair has `runs/<model>-<mode>/DONE` and is skipped;
  `report.py` regenerates `results.md` and the block below after every model.
- Launched as a **systemd user unit** so it survives the agent session:
  `systemd-run --user --unit=kairos-llm-ps --collect -p StandardOutput=append:…/logs/runner.log -p StandardError=append:…/logs/runner.log …/runner.sh`.
  Progress: `tail -f ~/kairos/vibeos-cuda-next/results/llm-ps-2026-09/logs/runner.log`,
  `systemctl --user status kairos-llm-ps`, `cat …/results.md`, per problem `runs/<model>-N/problems.jsonl`.

## 9. Caveats (read before drawing conclusions)

- **Contamination**: the newest LiveCodeBench problems date from Feb–Apr 2025; the 2026 candidates
  (Qwen3.5/3.6/3.8, Gemma 4, Bonsai) were trained after that, the baselines (Qwen2.5-Coder 2024,
  Qwen3-Coder mid-2025) mostly before. AIME 2026 (February 2026) is the cleaner set for the newer models.
- **Non-thinking mode** is what kAIrOS would run, but it handicaps the hybrid-reasoning models on AIME; the
  T runs for q35-9b and q36-35b-a3b show how much a 4096-token thinking budget buys.
- **1 sample per problem**: on 60 problems one pass is 1.7 pp; differences below ~8–10 pp are within noise.
- **Memory-bound runs**: the MoE models keep most experts in RAM here and the dense 27B only partially on the
  GPU — their tok/s are this laptop's numbers, not the 16 GB tier's; their pass rates are unaffected by that
  (but a 300 s per-problem cut-off hits slow models more often — `timeouts` is reported).
- The 1 GB sandbox memory cap can fail a legitimately memory-hungry solution; it is the same for every model.

# kAIrOS ❖ by mAIer

**kAIrOS** — from the Greek *kairos*, "the perfect, opportune moment", with **AI** for
**artificial intelligence** at its heart (k**AI**r**OS**). An operating system that builds
itself at exactly the moment you need it: inspired by [vibeOS](https://vibeos.sh/), but
**every model runs locally on your GPU**. No cloud, no API keys, no subscriptions, no
data ever leaving the machine — and it ships as a **bootable appliance**: flash the image
to a stick, boot it, and the desktop is there. Linux is underneath, but you never see it.

**Flexibility** — nothing is fixed. Apps don't exist until you summon them: name anything
("a pomodoro timer with rain sounds") and the artificial intelligence writes it as a
working app on the spot. Don't like it? Press the window's ✨ improve button and tell the
OS how to change it, in one sentence. Even the system's own utilities — file manager,
settings — are conjured the same way, and any app can reshape the OS itself through the
built-in API: themes, wallpapers, files, settings, WiFi, displays, even downloading itself
a bigger brain.

**Productivity** — everything is included, out of the box, offline: a coding AI that
writes your apps and tools, an image AI for pictures and wallpapers, a Python game forge
that ships playable desktop games, a full offline encyclopedia (English Wikipedia,
~12 GB), and **offline web search** — the same search API answers from the live web when
you're online and from the built-in knowledge base when you're not. One machine, one OS,
every creative tool already inside — so the moment an idea arrives, kAIrOS is the
opportune moment to build it.

**The browser browses an imaginary web.** kAIrOS never loads real websites — every
address under `/web/` is **generated by the AI on the first visit**, grounded in
web-search facts when online and in the offline encyclopedia when not. Type an address or
a question; the OS writes the site that should exist there, links and all (every link is
itself a prompt for the next page, sites stay consistent across their sub-pages). Pages
are cached, so everything you've visited keeps working with the network cable pulled.

The desktop shell (windows, dock, launcher, taskbar, Apps menu with AI-painted icons) is
real and instant. The *apps* are hallucinated: a local coding LLM researches the topic,
writes a spec, then writes a complete self-contained HTML app and the OS mounts it in a
window. Apps call local AI themselves — `vibe.ask`, `vibe.image`, `<img src="/genimg/a red
fox at dawn">` — and the **Arcade** forges pygame games that open as real windows on the
desktop.

**Living software — the system improves itself.** App code is temporary: a version runs
until you ask for the next one. The prompt of every started program is saved; ✨ improve
feeds the last version's code back to the model with one standing order: *implement new
features, fix bugs, improve*. v1 → v2 → v3… old versions stay on disk as history and as
input — never executed again; if an evolution fails, the previous version steps in.
Games evolve the same way. And the desktop remembers: the ◐ button paints a wallpaper
out of a shuffled memory of what happened this session.

**The everything-search.** A search field sits on the desktop, Windows-style — but it's a
*search prompt*: retriggered with every letter, randomized for serendipity, and it can
never come up empty. It finds your living apps, games, files on /data,
offline-encyclopedia articles, settings — and when nothing exists yet, it offers to
create it: summon the app, browse the imaginary web, imagine the image, forge the game,
dream the video. Press Enter and it exists.

**Never the same image twice:** every image/video generation rolls a fresh random seed.

## The stack (deliberately slim)

| Layer | Tech | Why |
|---|---|---|
| Image | Debian 13 (trixie) + systemd, **raw GPT `.img.gz`**: systemd-boot ESP + ext4 root that auto-grows on first boot | flash to any ≥ 64 GB stick or disk (the raw image is ≈ 51 GiB), UEFI boot, works offline; `kairos-install` clones it onto an internal disk (R48) |
| Desktop | tty1 autologin → X → **one Chromium desktop window over every connected monitor**: windows move between monitors, menu bar and dock on the primary, hot-plug without a reload (R90) | no boot menu, no kernel text, no login banner — a self-dreamed boot animation covers the warm-up (R27/R28) |
| LLM serving | [llama.cpp](https://github.com/ggml-org/llama.cpp) `llama-server` (CUDA, sm_89 + sm_120 PTX) | GGUF, fast, zero Python |
| Image **and** video | [stable-diffusion.cpp](https://github.com/leejet/stable-diffusion.cpp) `sd-cli` | one C++ binary covers Muse (a Krea 2 fine-tune), Qwen-Image, Z-Image, Chroma *and* Wan 2.2 video — no PyTorch, no ComfyUI |
| Music | ACE-Step 1.5 (turbo DiT + 1.7B LM, GGUF) via [acestep.cpp](https://github.com/ServeurpersoCom/acestep.cpp) `ace-lm` + `ace-synth` | pure C++/GGML like the rest; request-JSON driven, two stages; add-on download; built by `scripts/install-engines.sh` (CUDA since 2026-09-14, `docs/ENGINES-CUDA-2026-09.md`) |
| Knowledge | [kiwix-serve](https://kiwix.org) + `wikipedia_en_all_mini` ZIM (~12 GB, every tier) | offline encyclopedia; one static binary |
| Web | DuckDuckGo (keyless) with auto-fallback to kiwix | same `vibe.search` API online or offline |
| Kernel | `kernel/server.py` — Python + aiohttp | orchestrates models, swaps VRAM, RAG, the virtual web, self-repair loops |
| Hardware | `kernel/hw.py` → NetworkManager, sysfs, xrandr, timedatectl, bluetoothctl, pactl | `vibe.hw.*`: WiFi, battery, brightness, volume, power, displays, date/time, bluetooth, audio output |
| Shell | `shell/` — vanilla HTML/JS | window manager, dock, launcher, taskbar, vibe bridge |
| Games | python3 + pygame on the kiosk X display | generated games open as native windows next to the desktop |
| GPUs | NVIDIA R580 + CUDA 13.3 runtime; AMD iGPU firmware + Mesa Vulkan drivers (R30); a second, static Vulkan engine set in `bin/vulkan/` (`scripts/build-engines-vulkan.sh`) | hybrid laptops: NVIDIA computes, the iGPU drives the panel; NVIDIA-only desktops get nvidia-drm modesetting (R41); no NVIDIA driver → the kernel runs the Vulkan engines on the iGPU (`VIBEOS_ENGINE` overrides) |

**Self-healing generation:** app HTML is rewritten (links → `/web/`, pictures →
`/genimg/`), validated (truncation, unbalanced tags, external resources, fences) and
reworked by the LLM until clean; runtime JS errors inside apps are turned into a real bug
report (type, line, stack, code excerpt) and sent back for an automatic repair-and-remount;
generated games pass a syntax gate, then a launch test, with tracebacks fed back for up to
4 fix rounds. **Grounded imagination:** every app generation and `vibe.ask` is enriched
with facts from web search (online) or the local Wikipedia (offline); new apps get a
researched specification first. **Style mandate:** "modern and futuristic" is baked into
every UI prompt (apps, games, pages) — media prompts are left alone so the image model
paints what you asked for.

## Model tiers

| VRAM | HTML/app LLM | Python/game LLM | Image (default, baked) | Video (add-on) |
|---|---|---|---|---|
| 8 GB | Gemma 4 26B-A4B-it ultra-uncensored heretic i1-IQ4_XS (MoE, experts partly in RAM; `"uncensored": true`; also the quality translator) | shared | Muse v3.5 Extended Q4_0, no LoRA (1024²) | Wan 2.2 TI2V-5B Q4_K_M (add-on) |
| 16 GB | Gemma 4 26B-A4B-it ultra-uncensored heretic i1-IQ4_XS (same file and flags as 8 GB) | shared | Muse v3.5 Extended Q4_0, no LoRA | Wan 2.2 TI2V-5B Q8_0 (add-on) |
| 24 GB | Qwen3-Coder-30B-A3B Q4_K_M (full GPU) | Qwen2.5-Coder-32B Q4_K_M | Muse v3.5 Extended Q4_0, no LoRA | Wan 2.2 TI2V-5B Q8_0 (add-on) |
| 32 GB | Qwen3-Coder-30B-A3B Q6_K | Qwen2.5-Coder-32B Q5_K_M | Muse v3.5 Extended Q4_0, no LoRA | Wan 2.2 TI2V-5B Q8_0 (add-on) |

Every tier also lists three **add-on** image models — Qwen-Image (best text rendering),
Z-Image-Turbo (classic, fastest) and Chroma1-HD (uncensored) — downloadable in-OS with
`vibe.models.download(key)` and selectable per call or via the `image_model` setting
(R42/R47). VRAM strategy is **swap**: the LLM owns the GPU by default; image/video jobs
evict it, run, and the LLM lazily reloads (fast — the weights stay in the page cache).
Every image model carries a `max_pixels` budget so requests are auto-fitted to the card.
Manifests live in [manifests/](manifests/) and are plain JSON — swap any model you like.

**The uncensored default LLM.** On 8 and 16 GB the default LLM is the "heretic" edition of Gemma 4
26B-A4B, marked `"uncensored": true` in the manifest: it answers adult requests itself. When a model
still declines (a censored model, the image-prompt expander), the kernel never caches or renders the
refusal: R86's ladder retries with an 18+ system preamble, then on the uncensored model, and only
then answers "declined" (HTTP 422). The one content block is narrow: a request that pairs an
explicit under-18 age or word with a sexual term (plus a few illegal-content terms) is refused
before any model runs — there is no other filter (`docs/REFUSAL-FALLBACK-2026-10-09.md` §11).
Stock Gemma 4, Krea 2 Turbo and the Kroma LoRA left the manifests on 2026-10-10.

**One image fits everyone:** the shipped image embeds only the 8 GB starter set (< 58 GiB
in total, R47). At first boot the OS reads the GPU's VRAM and shows a welcome dialog
offering to download the matching tier in the background (OS stays usable, brain switches
live when done). Decline and upgrade later from ⚙ Settings — apps can drive it too via
`vibe.system.upgrade(tier)`.

**Images.** None is published yet. The current builds (v7.5-1, on the owner's machine) are the
**v7.5-1 hotfix kit**, which brings an already flashed v7.5 stick to v7.5-1 (Muse and the heretic
LLM replace Krea 2, the Kroma LoRA and stock Gemma; with a rollback), and
**`kairos-hwtest-4070-v7.5-1-media.img`** — 80.5 GB, the same system with the video and music
add-ons pre-installed, for media of **128 GB or more**. See
[docs/how-to/BUILDING.md](docs/how-to/BUILDING.md) §4.

**Public images (R87, 2026-10-16).** Shareable images switch on a build-time profile (`/etc/kairos/profile` =
`public`, written by `scripts/public-image-prep.sh`). Muse has no redistribution grant, so a public image never carries it:
its default picture model is **Z-Image-Turbo** (Apache-2.0) with Muse's prompt rules, and the user can add Muse at first
start or in ⚙ Models & licences **with their own civitai API key** (stored root-only, sent to civitai only). A **minimal**
image bakes only the LLM and fetches the rest at first boot (resumable, sha256-checked, waits while offline; every
feature says "downloading …" until its model is there). The prep script removes every private bit (WiFi, SSH keys,
logs, histories, machine-id, …) and has a `--verify` mode. Without the profile file — the owner's images — nothing
changes. Details: [docs/PUBLIC-IMAGES-2026-10-16.md](docs/PUBLIC-IMAGES-2026-10-16.md).

> The tables follow `manifests/tier-*.json` as of 2026-10-14; the manifests are the truth.
> Generating the tier table from them is a seed issue.

## Requirements

**To run the test suite or hack on kernel/shell:** any Linux (or macOS/WSL2) with Docker.
No GPU, no models, 2 GB of disk. The suite's container has no network access.

**To run the real kernel on your own GPU:** Linux, an NVIDIA GPU with **8 GB VRAM or more**
and the R580+ driver (or an AMD/Intel GPU with Vulkan for the slower static engine set),
32 GB RAM recommended, a Debian 13 environment with root to build the engines (hours), and
26.4 GB of model weights for the baked 8 GB set — about 102 GB with every add-on and the
Wiktionary ZIMs, plus the 12.5 GB Wikipedia ZIM.

**To build or test the appliance image:** root on a Debian/Ubuntu host, ~120 GB free, the
12 GB Wikipedia ZIM; a 64 GB USB stick (or bigger) to flash; for the VM rig Docker with
`/dev/kvm`, and for GPU passthrough a second GPU (or headless host) plus IOMMU.

### Dev setup (the kernel on a plain Linux box)

The kernel runs on any Linux box with the engines under `/opt/vibeos` — no image needed:

```bash
scripts/install-engines.sh                                   # llama.cpp + sd.cpp (CUDA), once
python3 scripts/download-models.py manifests/tier-8gb.json   # models for your tier (every entry, ~103 GB; the baked set only: dev/tools/download-baked-models.py)
scripts/download-knowledge.sh                                # the Wikipedia ZIM
scripts/start-vibeos.sh            # -> open http://localhost:1337
```

The automated suite boots the kernel on **mock engines** (no GPU) and needs
`python3-aiohttp` plus trixie's `quickjs`; the in-repo container provides that environment:

```bash
bash dev/docker/run-suite.sh       # = tests/run-tests.sh in dev/docker/Dockerfile.kernel-test, --network none
```

On 2026-10-14 the full suite on this tree gave **291 passed / 0 failed / 8 skipped** in the default
`--network none` mode and **292 / 0 / 7** with `KAIROS_TEST_NET=internal` (nine result files, each
0 failed; the standard data mounts present — without a Wikipedia ZIM one more test skips);
[docs/how-to/TESTING.md](docs/how-to/TESTING.md) lists every skip and why.

### Building the appliance image

```bash
# on a build host with multi-arch engines + the 8gb models + the ZIM under /opt/vibeos:
sudo bash iso/build-iso.sh     # live-build rootfs (intermediate squashfs)
sudo bash iso/build-img.sh     # -> kairos-hwtest-4070.img.gz  (GPT, systemd-boot, auto-resize)
# flash: gunzip -c kairos-hwtest-4070.img.gz | dd of=/dev/sdX bs=4M conv=fsync   (see iso/flash-img.md)
```

See [iso/README.md](iso/README.md) for what is on the image and how recent releases were
actually produced (flattened from the testrig VM — the rig is now in `dev/rig/`).
`scripts/build-image.sh` is the pre-appliance WSL tarball builder and is not the product.

## Repo map

- `kernel/server.py` — the OS kernel: model manager (VRAM swap), app generation (SSE,
  research → spec → code → rewrite → validate → repair), the virtual web (`/web/`), the
  picture tool (`/genimg/`), image/video/music job queue, pygame forge, installer, setup
- `kernel/hw.py` — the laptop-setup API (WiFi, battery, brightness, volume, power,
  displays, date/time, bluetooth, audio output)
- `kernel/vfs.py` — Android-style filesystem: write-protected `/system`, formattable `/data`
- `kernel/knowledge.py` — web search (online) / kiwix Wikipedia (offline), one interface
- `kernel/boottime.py` — boot-duration history for the boot screen's loading bar [R73];
  `kernel/sessionlog.py` — the session log behind the self-painting wallpaper [R44]
- `kernel/prompts.py` — the system prompts that define what kAIrOS apps look like
- `docs/API.md`, `docs/api/*.md`, `docs/wiki/*.md` — the API documentation and recipes
  **for the coding LLM** (injected into every generation, `/api/docs`, `vibe.docs()`;
  there is deliberately no user-facing docs app — R46)
- `shell/` — desktop: window manager, dock, summon launcher, App Launcher, built-in studios
  (Imagine/Motion/Arcade/Music), taskbar, `vibe.*` bridge injected into every app
- `manifests/tier-*.json` — model picks, add-ons, serve/gen args per VRAM class
- `iso/` — live-build config, `build-img.sh`, systemd units (kiosk, bootlog, boot screen,
  installer), the initramfs hook/scripts of the boot screen, QEMU verifiers
- `scripts/splash/` — the boot screen [R73]: `kairos-splash.c` (static framebuffer painter
  started from the initramfs: firmware logo + kAIrOS lockup, then the thick logo + loading
  bar), `render-assets.py` (the logos, from the shell's font), `install.sh`;
  `shell/boot-wait.html` continues the bar inside the kiosk until the kernel answers
- `scripts/` — engine builds, manifest-driven downloads, `update-progress.py`
- `docs/REQUIREMENTS.md` — every owner request as numbered requirements (R1–R86), with
  status notes where a later requirement superseded an earlier one
- `docs/PROGRESS.md` — auto-generated: implemented vs implemented-and-tested per requirement
- `docs/SESSION-HANDOFF.md` — the chronological build log; `docs/MODEL-REFRESH-2026-09.md` —
  the current model/licensing audit; **[docs/README.md](docs/README.md)** — the index of
  all ~40 dated reports by category
- `docs/how-to/` — getting started, testing, building, the VM rig, architecture
- `tests/` — mock engines + `run-tests.sh`: boots the kernel and tests every requirement;
  regenerates PROGRESS.md. Claude workflow `kairos-verify` runs it + repairs failures.
- `dev/` — the in-repo test container (`docker/`), the VM test rig with VFIO passthrough
  (`rig/`), the seed issues (`issues/`), small tools (`tools/`)
- `bench/` — benchmark harnesses and prototypes
- `CLAUDE.md` — how Claude Code sessions work in this repository (project map, suite, the
  verification culture, the commit rule); `CONTRIBUTING.md`, `SECURITY.md`, `CODE_OF_CONDUCT.md`

See [docs/DESIGN.md](docs/DESIGN.md) for architecture details, or start with
[docs/how-to/ARCHITECTURE.md](docs/how-to/ARCHITECTURE.md).
